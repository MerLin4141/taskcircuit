# TaskCircuit v0.1.2 Scheduler Duplicate Firing 调查

## 结论与适用范围

**正常业务 API 加上系统时钟回拨可以产生该状态。** 这不是只会由人工篡改产生的数据库状态。通过公开 API 创建每分钟 Cron，在一次 tick 已选中到期计划后、计算下一次 Cron 时间前令注入的时钟向后回拨；事务提交后，该 Schedule 仍为 active，`next_fire_at` 与刚创建的 firing 的 `scheduled_for` 相同。时钟再次达到该时间，下一次 tick 命中唯一约束并失败；更晚到期的另一条正常 Schedule 也被阻塞。

复现使用受控 `clock` 模拟墙上时钟回拨，不修改临时数据库；没有对真实系统时钟操作。它证明该业务路径在提供的时钟序列下可达，并非证明真实系统中已经发生过。复现测试和原始人工注入测试均保留失败断言；本轮未修业务代码。

## 根因和代码位置

`src/hub.ts:693` 的 `tickScheduler()` 先通过 `now()` 得到事务时间，并选择 `next_fire_at <= time` 的 active Schedule（`:699-704`）。插入 firing 后，Cron 的下一次时间却用第二次 `clockNow()` 计算（`:806-815`，调用 `src/scheduling.ts` 的 `nextCron`）。如果第二次读数小于刚触发的 `scheduled_for`，下一次 Cron 时间可能等于、甚至早于已提交的触发时间。事务随后在 `:817` 提交相互矛盾的业务状态，SQLite 的唯一约束并未禁止这一跨表组合。

测试 `tests/scheduler-failure-investigation.test.ts` 的 `F clock rollback`：

1. 在 00:00 通过 `/api/schedules` 创建 `* * * * *` Cron；下次为 00:01。
2. 时钟到 00:01，tick 选中并插入 firing；在同一个 tick 内计算下次 Cron 时，测试时钟回拨到 00:00。
3. 第一次 tick 正常提交 1 条 firing、1 个 Work Item、1 个 Execution，但 Cron 仍 active，`last_fire_at = next_fire_at = 00:01`。
4. 测试时钟前进至 00:01:01，下一次 tick 抛出 `UNIQUE constraint failed: schedule_firings.schedule_id, schedule_firings.scheduled_for`；另一条 00:01:01 到期的一次性计划保持 active，未产生 Work Item。

按 `next_fire_at,id` 排序的最早异常记录会被反复选中；回滚不修正它。`src/hub.ts:833-847` 的后台定时回调捕获异常并记录失败，而当前 tick 不继续处理后面的 Schedule。独立的双计划人工注入测试也连续两次观察到后者被阻塞。

## 数据模型与约束

`src/migration.ts:17-19` 是实际 schema；项目没有独立的 Schedule/Firing TypeScript domain interface。实际列名是 `next_fire_at` 和 `scheduled_for`，不是问题示例中的 `next_run_at` / `scheduled_at`。

- `schedules.id` 是主键，`config_key` 唯一；字段包括 `kind`、`status`、`owner_kind`、`owner_id`、`reason`、`parent_execution_id`、`run_at`、`next_fire_at` 和 `last_fire_at`。`schedules_due(status,next_fire_at)` 仅是普通索引。
- `schedule_firings.id` 是主键，`schedule_id` 引用 Schedule；`event_id` 和 `execution_id` 可空且引用各自记录；`scheduled_for` 是本次计划时间，`created_at` 是创建时间。Firing 没有 status 字段或单独的完成状态，链接通过事务内更新 event/execution ID 写入。
- 一个 Schedule 允许多个不同时间的 Firing；`UNIQUE(schedule_id,scheduled_for)` 只禁止同一计划的同一计划时间再次插入，不保证 Schedule 的状态与时间指向尚未触发的时刻。schema 中没有该跨表不变量的 CHECK/触发器；`status` 本身也没有枚举 CHECK。
- 公开 resume 只允许 user-owned、paused 的计划变 active，保留原 `next_fire_at`；不能把 completed 或 cancelled 恢复为 active（`src/hub.ts:607-647`）。一次性计划正常触发后 completed 且 next 为 null。Cron 正常触发后仍 active 并推进下一时间，但时钟回拨会让其复用已经触发的时间。

## SQLite 事务与崩溃

`src/hub.ts:73-82` 的 `tx()` 实际执行 `BEGIN IMMEDIATE`、同步回调、`COMMIT`；异常时 `ROLLBACK` 并重新抛出。数据库启用 WAL、foreign keys 和 5 秒 busy timeout（`:57-61`）。每一条被选中的到期 Schedule 各有一笔事务；tick 开始的执行过期处理是另一笔事务，整个 tick 批次不是一个事务。

| 中断时机                      | 恢复后的数据库状态                                                                                                                                              |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| firing 插入前                 | 本次计划处理无提交；原 active/next 保留。                                                                                                                       |
| firing 已插入、计划未更新前   | 未提交事务回滚，firing 和同事务产生的事件/任务一起消失，原 active/next 保留。实际强杀测试命中这一窗口并在重启后验证。                                           |
| 计划更新后、COMMIT 前         | 同一 SQLite 事务仍应整体回滚；根据事务实现推断，未单独在此精确位置强杀。                                                                                        |
| COMMIT 成功后                 | firing、关联记录和 Schedule 更新一起持久化；正常单调时钟下重启不重复触发。若该事务内出现上述时钟回拨，提交的业务状态本身可能已经不一致。                        |
| COMMIT 成功而调用方未收到结果 | 数据库事务仍已提交；tick 是内部同步函数，并无独立的外部 HTTP firing 响应可测试。重启/再次 tick 的正常无回拨路径已验证；不把它当成外部副作用 exactly-once 保证。 |

普通进程崩溃在所测插入后窗口不会产生“只插入 firing、未推进 Schedule”的半提交状态；代码和事务原子性支持其余未提交窗口回滚，但非穷尽式证明。**时钟回拨是已复现的另一条路径**，不是 SQLite 事务失效。

## 建议的最小修复，待审核后实施

1. 在同一 Schedule 事务中使用选取到期项时捕获的 `time` 计算下一次 Cron，而不是重新读取墙上时钟。已选中保证 `scheduled_for <= time`；因此应验证 `nextCron(expression, timezone, Date.parse(time))` 严格晚于 `scheduled_for`。保持现有 fire-once/跳过错过时刻的语义；还需测试时区/DST、时钟前进/回拨、边界时间、并发和正常多次 Cron。
2. 现有数据库可能已经处于异常状态，仅阻止新问题不够。设计有明确可观测记录的隔离/修复策略：事务内识别**同一 Schedule、同一时间确有既存 Firing**，不再次创建 event/Work Item/Execution；对不一致 Schedule 做有界隔离，允许其他到期计划处理。具体是暂停并要求人工核实，还是按严格晚于已触发时间推进，应结合 owner 类型和既存 firing 关联完整性审核，不能无条件静默吞错或使用 `INSERT OR IGNORE` 处理所有约束。
3. 测试记录修复后同一 tick 继续正常任务、已有 firing 和引用不变、其他约束错误仍抛出、反复重启/并发不产生副作用，以及异常 Schedule 可观测。保持原始和时钟回拨失败测试作为回归测试。

需要业务代码修复；当前没有证据表明必须新增 Migration。不能仅靠唯一约束解决饥饿，也不能声称外部副作用 exactly-once。

## 修复记录：Tick 时钟一致性与异常隔离

### 修复范围与时钟

`src/hub.ts` 的 `tickScheduler()` 在入口读取一次 `clockNow()`，将其转换为本次 tick 的 ISO 时间。到期查询、Cron 下一次时间、Schedule 更新、调度创建的 Event/Work Item/Execution 时间和过期 Execution 扫描均使用该快照。`createEvent` 和 `expireExecutions` 接受调用方提供的时间；其他调用路径仍按原行为读取时钟。每个 Schedule 处理仍各自处于原有 `BEGIN IMMEDIATE` 事务内，前置过期扫描仍是独立事务。

Cron 仍使用墙上时钟和原有五字段解析器，以 tick 快照为起点计算严格晚于该时刻的下一触发时间；保持错过多个触发时间时 fire-once、然后从当前时间推进的语义。没有引入单调时钟。现有时区回归及新增纽约夏令时转换、六字段拒绝测试通过。

### 异常 Schedule 的隔离

在写事务内、插入前精确查询 `(schedule_id, scheduled_for)` 的现存 firing；`BEGIN IMMEDIATE` 防止其他写事务在检查与插入之间竞争写入。只有查询到相同键的记录才按重复 firing 处理；没有捕获或忽略其他 SQLite 约束错误，也没有 `INSERT OR IGNORE`。现存 firing 不修改，Schedule 保持原状态和时间；无论 firing 关联完整与否，都不假设其安全，也不自动推进、取消或完成。

当前 tick 在内存中记下异常 Schedule ID，从后续到期查询中排除该 ID，继续处理其他计划。每次发现异常会输出 JSON 诊断，包含 `type: schedule_firing_duplicate`、`scheduleId` 和 `scheduledFor`，不包含 token 或凭据。这是**单次 tick 的非持久隔离**：后续 tick 或 Hub 重启会重新发现并记录异常，需要人工检查和修复；每个 Hub 进程独立隔离。大量异常计划会增加查询参数数量和反复诊断，尚未做规模性能验证。未新增数据库字段或 Migration。
