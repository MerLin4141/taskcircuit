# v0.3 Phase 3 Source Plugin report

## Before and after

The v2 HTTP ingress constructed `local-cli` and `trusted_local_cli` directly before calling Event Core. It now obtains an explicitly bound Source Plugin from a Hub-owned registry. The builtin `local` plugin normalizes input into the existing EventEnvelope and trusted source context. Event Core remains plugin-agnostic. A trusted in-process binding permits isolated tests to register another Source; neither HTTP payload nor CLI display source selects it.

## Trust and compatibility

Local Source code is trusted; incoming event content remains untrusted. The loopback check is transport restriction, not authentication. Existing Event Core validation, persistence, correlation, same-identity duplicate and changed-content conflict remain authoritative. Unknown valid event types remain persisted as unroutable without a Root. The legacy `/api/events` path and scheduler-owned Cron, Retry and Later are not pluginized. No schema migration or new configuration or CLI syntax is introduced.

## Verification and remaining work

`tests/source-plugin-integration.test.ts` exercises builtin identity, HTTP ingress, source spoof attempts, duplicate/conflict, unroutable persistence, isolated registries, missing source, rejected input and a test-only Source through the Hub. Existing event tests retain coverage for routing, correlation, parent trust and size limits. Source polling/watch lifecycle, external loading, production source configuration, and Channel migration remain future work. Trusted plugin code is not sandboxed and can do what the OS user can do.
