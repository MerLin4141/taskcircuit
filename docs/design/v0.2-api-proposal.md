# TaskCircuit v0.2 — API、CLI、状态与反馈提案

> 以下 endpoint 是设计，不是 v0.1.2 已实现功能。统一沿用 `/api` 前缀；新写 API 默认仅可信本地操作者，身份/跨用户授权并非当前能力。请求大小、schema version、持久 idempotency key、error envelope 和 rate limit 在实现前固定。Legacy endpoints 和回执契约继续可用；不为外部不可信请求提供无认证公网入口。

## 资源接口

| 方法与路径                                                                                         | 语义、身份和并发                                                                                                                                              |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/automations`、`GET /api/automations`、`GET /api/automations/:id`                        | 仅可信管理者创建定义/读定义与版本；create 用 idempotency key，配置引用校验，不接受 payload 传 executable 或权限。                                             |
| `POST /api/automations/:id/versions`                                                               | 创建不可变 revision；要求 expected version；旧 Root 继续旧 revision；禁用只阻止新 Root。                                                                      |
| `POST /api/events/v2`                                                                              | source identity 来源于可信接入上下文，body 含 source-event ID/type/payload/occurred time；同 source+ID 同摘要读回，异摘要 409；不允许 body 赋予 source 权限。 |
| `GET /api/roots/:id`、`GET /api/roots/:id/work-items`、`/events`、`/decisions`、`/timeline?after=` | 返回独立、可分页、可解释的状态；审计字段最小化，游标和不可用历史明确。                                                                                        |
| `POST /api/roots/:id/cancel`                                                                       | 按预期 version 和稳定 request ID 幂等取消；事务禁止新增工作，记录原因并请求停止执行，不声称外部副作用撤销。终态 409 或返回既有取消 receipt。                  |
| `POST /api/interactions/:id/answer`                                                                | 保留旧请求兼容；v2 可追加 response ID/expected revision。Input 只提供数据；approval 另有类型/身份/过期/动作摘要（SHOULD）。                                   |
| `POST /api/executions/:id/result`、receipt query                                                   | v0.1.2 保留；同 submission 和 digest 返回原 receipt，旧 token 不可写新结果；Receipt 证明 Hub commit 而非外部事实。                                            |

请求示例（路径仅提案）：`POST /api/events/v2` body `{ "type":"issue.updated", "sourceEventId":"delivery-123", "payload":{...}, "occurredAt":"2026-01-01T00:00:00Z" }`；可信接入器另行绑定 source instance，不将 body 的 `rootId` 当权限。对内部 feedback 在同一控制面事务中用 execution/parent event 继承 root，不接受 Agent 自报跨 Root。

CLI 草案：`taskcircuit automation create <file>`、`automation list`、`event emit <type>`、`root show <id> [--json]`、`root cancel <id>`、`root events <id>`、`root decisions <id>`；输出稳定 ID、原因码、未知结果和预算；不得展示 token。保留现有 `work`, `schedule`, `emit`, `answer`, `hub`, `worker`, `runtime` 实际命令；v0.1.2 未发现 `taskcircuit run` 顶层命令，不能承诺该不存在命令，若指 `runtime run` 则保留。

## Work Item 状态迁移（新模式内部投影；旧 API 兼容映射）

| FROM                           | EVENT / guard                              | TO                                | Authorized by              | Persistence effect                                                 |
| ------------------------------ | ------------------------------------------ | --------------------------------- | -------------------------- | ------------------------------------------------------------------ |
| absent                         | 已去重 Event + decision + root active      | queued                            | trusted policy             | 写 WI、decision、root 关系、首执行意图、budget reservation         |
| queued                         | 有效 lease、Root 不终态且未超预算          | running                           | Hub claim                  | 原子租约/epoch + root active slot                                  |
| running                        | complete 且完成条件成立                    | completed                         | policy after fenced result | result receipt、session、决策、settlement、timeline                |
| running                        | input / later                              | waiting                           | policy                     | interaction 或 schedule；释放 active slot，保留计量事实            |
| waiting                        | input answered / schedule fired、Root 活动 | queued                            | policy + budget            | 唯一 trigger key、预留、创建后续 Execution                         |
| running                        | safe failed 且 retry policy/预算允许       | waiting                           | policy                     | safe retry schedule，不因 timeout 猜安全                           |
| running                        | unknown/失权且结果无法确认                 | blocked                           | Hub recovery               | failed+unknown error、reservation freeze，不建重试                 |
| blocked                        | 人工核实 + expected revision + 未过期      | queued / completed / failed       | trusted operator + policy  | 证据与决定、重新预算校验；不得直接删除旧证据                       |
| queued/running/waiting/blocked | Root cancel/expiry                         | cancelled 或保留 unknown 审核投影 | trusted operator / policy  | 禁止新执行、撤销等待、请求 abort；在途外部结果无法证明时留 unknown |
| completed/failed/cancelled     | 任意新 Event                               | 无转换                            | n/a                        | terminal WI 不 reopen；新 Root / 新 WI 及只读 predecessor          |

映射：新 `queued/running` 对旧 `active`；`waiting` 对旧 waiting_input/waiting_schedule；`blocked` 对旧 failed+unknown 的诊断视图，避免旧客户端不识别状态。实现须避免新状态直接泄漏旧 API。

## Execution / Interaction 状态

新模式 Execution 物理兼容现有 `queued → running → completed/failed/waiting_input`；`leased` 是取得租约与 running 的逻辑阶段，当前原子 claim 并不单独持久化 claimed。Later 返回后执行 completed、WI waiting；Retry 使用新 Execution 记录，原失败不改写。逻辑 unknown 映射 failed+`execution_outcome_unknown`，限制所有自动重试。retry_scheduled 是 Schedule 状态而非伪造旧 Execution 重开。旧 token 对新提交一律 409，只有完全相同已接受 receipt 可只读确认。

Interaction：input `open → resolved/cancelled/expired`；answer 带 revision/幂等 ID，复用既有已解析回答，冲突答复 409。approval（SHOULD）`pending → approved/denied/expired/revoked`；必须绑定主体、root、policy hash、plan/action/workspace digest、revision、expiry，变更需重审；没有经过真实认证不开放远程审批。旧 Interaction `open/resolved/cancelled` 映射 input，旧 answer 不升级为批准。

## 反馈联合类型和后继

| Feedback       | 意义 → 运行时决策                | Root / WI / Execution                                         | 预算 / 人                                      |
| -------------- | -------------------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| Completed      | 建议完成；验证完成条件           | all done 时 Root completed，WI completed，Execution completed | settle；无人工                                 |
| Continue       | 建议下一轮；重新检查策略与熔断   | Root active，WI queued，新 Execution；旧 completed            | settle + 新 reserve；无直接递归                |
| NeedsInput     | 缺少资料                         | Root/WI waiting，Execution waiting_input                      | settle，建 input interaction；答复后重新决策   |
| NeedsApproval  | 请求许可，不是许可本身（SHOULD） | waiting，Action 未发送                                        | settle；绑定快照与身份的 approval              |
| Later          | 建议将来重评                     | waiting，Execution completed                                  | settle；持久 schedule，触发重新授权            |
| Failed         | 报告失败                         | failed 或 waiting retry；Execution failed                     | settle；只有可靠安全证据允许 Retry             |
| EmitEvent      | 请求内部子事件（受控可选）       | 继承 Root 和 parent，策略可拒绝                               | 深度/调用预算；不能由其自定 Root               |
| ProposedAction | 建议动作（SHOULD）               | waiting/blocked 或拒绝；不可直接发送                          | 策略、审批及动作预算；无 OS 保障时 fail closed |
| Stop           | 请求停止                         | 经策略终止/blocked；旧执行 completed 或 failed                | settle；终止原因可追溯                         |
| Unknown        | 无法确定结果，包括终止/回执丢失  | Root/WI blocked；旧 Execution failed+unknown                  | freeze reservation，人工或可信查询；不自动重发 |

Root Timeline 同事务记录 event→decision→execution→feedback→interaction/action→budget→终态的 ID、reason、版本与时间；外部数据和秘密按最小保留，不从可裁剪 SSE 推断全历史。未找到的历史证据标 unavailable。

## Phase 2 已实现的 Event Core 接口

以下接口是独立 Event Core 路径；旧 `POST /api/events`、`emit <type>` 和 `work create <type>` 保留原有创建 Work Item 的行为。新路径不会创建 Work Item、Execution 或启动 Agent。

- `POST /api/events/v2`：本机 loopback 入口。请求可包含 `sourceEventId`、`type`、`payload`、可选 `automationId` 或 `automationIds`、`correlationKey`、`occurredAt` 和仅供展示的 `displaySource`。服务端固定可信 source instance 为 `local-cli`；正文中的 `sourceInstance`、`trustContext` 和 payload 内控制字段不赋权。该入口不能提供 parent 关系；可信内部调用通过独立上下文继承父 Root。
- `GET /api/events/v2`：按 received time 返回最多 100 条新事件摘要，不包含 payload；`GET /api/events/v2/:id` 查询新事件、投递、Root 关联和最多前 100 条生命周期记录。`GET /api/events/:id` 也可读取历史事件，历史来源和 Root 证据可能不可用。
- `GET /api/roots/:id/events?after=<sequence>`：按持久关联序号分页，每页最多 100 条，默认返回摘要而非 payload。事件发生时间来自来源，不用于授权或顺序保证。
- `taskcircuit event emit <type> [--source 名称] [--source-event-id ID] [--correlation-key 键] [--automation ID] [--payload JSON]`；`event show <id>`、`event list` 为只读查询。未提供 source-event-id 时 CLI 为每次调用生成新 ID，重放幂等需要调用方复用 ID。`--source` 只设置显示名称。

常规入口无匹配类型或未选定 Automation 时，合法事件持久化为 `unroutable` 且不建 Root；可信内部子事件可按校验过的父 Root 继承。使用一个或多个本机可信指定的 Automation 时，同一 Event 可关联多个不同 Automation Root；同一身份同摘要返回 `duplicate`，不同摘要返回 409 和冲突审计。所有 Root 关联、Event 与投递记录在同一事务提交。

Loopback 限制不是用户认证：同机其他进程仍可能调用本地端口，Trusted Local 不构成 OS 级隔离。默认日志不记录完整 payload；凭据字段与已知凭据形态的拒绝是尽力检测，不能保证识别所有秘密。当前 `event show` 会返回已保存 payload，调用方应避免提交凭据并谨慎处理输出。接入真实外部来源、跨用户授权及凭据隔离需后续独立设计。

Phase 2 不提供新的公开 Automation 创建 CLI 或 REST API；使用 `--automation` 前必须已有可信控制面创建的 Definition。一个 Event 的多个 Automation 目标由本机可信调用方通过 `automationIds` 显式指定，不能从 payload 派生；相同 Event 不会关联同一 Automation 的多个 Root。

## Phase 3 decision endpoints

- `POST /api/events/:id/decide`: loopback-only write with `requestId`, `rootId`, optional positive `generation` (default 1), and optional `expectedRootVersion`. Policy, agent, workspace, capability and other authority fields are rejected. An identical request or logical evaluation returns the committed fact; a conflicting identity returns 409.
- `GET /api/decisions/:id`: read a committed decision.
- `GET /api/roots/:id/decisions?after=<sequence>`: up to 100 decisions in local sequence order.

The Hub evaluates newly correlated events after Event commit, and scans for pending event-root links on startup and during normal polling. An Event marked `processed` is only an Event Core fact; it does not claim that an Agent executed. The automatic scan starts after the migration watermark, so pre-existing Event records do not get invented historical decisions. This is local control-plane access, not authentication.

## Phase 4 materialization

`POST /api/decisions/:id/materialize` is a loopback-only internal control-plane operation. It returns the durable Work Item/Execution relation for a previously authorized Decision and returns the existing relation on replay. It does not start the Agent. A terminal or blocked Root, changed trusted profile/workspace or invalid plan is rejected. Local loopback is not authentication. Hub recovery scans for eligible pending Decisions after committing Event/Decision work; failures remain pending and produce a diagnostic with decision ID and reason code.

Continue and Stop are new additive Agent result types on the existing execution-result endpoint. They retain the existing submission identity, digest, receipt, lease and fencing semantics. A Continue is persisted as a pending request rather than launching another Agent. Root-wide cancellation and the Phase 5 launch limits are not provided by these endpoints.
