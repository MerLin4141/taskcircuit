# TaskCircuit v0.2 Phase 4 — Minimal Feedback Loop

## Scope and safety

The phase links an authorized immutable Decision to a durable Work Item and queued Execution. Migration 9 is required for a unique, durable Decision-to-Work-Item relation without mutating a Decision or relying on mutable Work Item metadata. It affects generation 2 only. Authorized Decisions recover after restart; repeat materialization returns the existing relation. The transaction validates Root state and immutable plan, checks registered profile/workspace against the trusted snapshot, and preserves the Root ownership. A pending Decision prevents premature Root completion.

Agent result handling adds `continue` and `stop` while keeping the existing complete, ask/needs_input, later and fail forms. Continue is committed as structured Execution output with the Work Item waiting; no continuation is automatically started. Stop terminates only that Work Item without retry. The existing session, receipt, result digest, stale-worker fencing, unknown-outcome and cancellation paths remain in use. Ask and Later reuse the existing Interaction and Scheduler mechanisms.

**Automatic automation Agent launches are disabled.** The central claim predicate rejects automation Roots because Phase 5 has not yet implemented a durable atomic `max_runs`/deadline gate. Consequently this phase does not demonstrate an end-to-end automatic Decision → Agent → Continue → Agent loop. A queued Execution is not proof of an Agent invocation. The existing Worker derives a per-work-item directory under `workspaceRoot`; the future automation launch implementation must explicitly resolve and test how the frozen Decision workspace is honored and revalidate the trusted path and profile before enabling execution. Capabilities remain metadata, not OS isolation. External side effects are not exactly-once, and killing a process cannot undo them.

## Evidence and boundaries

The phase uses isolated SQLite databases, deterministic fake CLIs and controlled processes. Tests cover idempotent same-Decision materialization, concurrent processes, blocked/terminal Roots, changed trusted configuration, Root aggregation with pending work, schema 9 crash/reopen and future-schema rejection, normalized Continue/Stop, result receipt and post-commit response loss, and old protocol regressions. Real Codex/Claude, the formal user Runtime/database and Windows reboot/logon are not used. Root-wide cancellation, ActionIntent, outbox, plugins, external action dispatch and Loop Limits are not implemented.

Full regression results and remaining phase-gate gaps are recorded after actual validation; no claim about real Agent compatibility follows from fake CLI output.

## Isolated verification

Before transfer, the complete suite passed **32 files / 363 tests**, with zero failures and no skipped tests. Typecheck, formatting, build and npm audit also passed; the audit reported zero vulnerabilities. The previous Phase 1A–3 and P0/P1, scheduler, fake CLI and Windows Runtime automated regression tests ran as part of that suite. The fake CLI tests include Continue → Continue → Complete through one simulated session, but they do not bypass the disabled automation claim gate or prove autonomous real-Agent execution.

The claim selection is the single current launch admission point; it denies every automation Root until Phase 5. Because no automation Agent is admitted, Decision/continuation authorization and `max_runs`/deadline have not yet been implemented as an affirmative launch gate. Phase 5 must implement and test those checks together with workspace revalidation and the existing Root concurrency and fencing requirements before opening the gate. Root-wide cancellation remains unavailable.
