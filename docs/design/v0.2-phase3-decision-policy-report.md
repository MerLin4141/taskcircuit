# TaskCircuit v0.2 Phase 3 — Decision / Policy Core

## Scope and choices

The Event Core's committed event-root links are the input to a separate policy step. The built-in deterministic policy uses the Root's pinned immutable Definition Version and locally registered profiles and workspaces. A Decision is an immutable authorization fact; the phase creates neither a Work Item nor an Execution. The user explicitly selected a `create_work_item` intent and keeping a newly created Root in `created`. The immutable policy identity is `taskcircuit-policy-v1` plus the SHA-256 of the canonical Definition Version snapshot.

## Schema and semantics

Migration 8 operates only on generation 2 at schema 7, and atomically creates `decisions`, `decision_requests`, and a migration activation watermark. The database prevents decision mutation, binds decisions to an existing event-root link and pinned definition, and uniquely identifies an evaluation by event, root and positive generation. A request ID and canonical digest make retries idempotent; conflicting reuse returns a conflict. Stable SQLite sequence orders each Root's timeline. A new generation is a new evaluation, not a retry. No historical decision is invented for event-root links preceding activation.

Policy decisions can authorize, ignore, block, wait, or reject. Terminal and blocked Roots cannot be authorized. Missing or changed agent profiles, invalid or changed workspace registrations, and capability escalation fail closed. Approval requirements produce `wait` without implementing an approval workflow. Event payload cannot select agent, workspace, capabilities, trust, or bypass policy. `external_action` remains denied. An authorized plan stores the selected profile ID, normalized workspace path, capabilities, reason, identity and existing Work Item or intent. It does not materialize or execute that intent.

## Recovery and concurrency

Event ingestion commits independently before the policy step. The Hub scans post-activation links without generation-1 decisions on startup and periodic processing. The unique constraint and transaction allow concurrent writers and lost-response retries to converge on one fact. Migration and decision transaction fault injection uses temporary SQLite files and controlled child processes. A pre-migration Event remains historical; a post-activation Event can be recovered without rerunning an Agent.

## Security and limitations

Paths are checked for existence and normalized using real paths against a trusted allowed root at evaluation time. A path or registration can change afterwards; a future execution phase must revalidate it. Capabilities are policy metadata, not OS-enforced permissions. Trusted Local is not a sandbox, loopback is not authentication, and same-user malicious processes are outside the boundary. No external actions, policy scripting, approval workflow, Root Budget, plugin system or autonomous Agent execution is introduced. Diagnostics do not deliberately log payloads or credentials.

## Verification

The pre-change baseline passed format, typecheck, build and 303 tests across 26 files. The Phase 3 tests cover pure policy, malicious payloads, immutable decisions, duplicate and conflicting requests, multi-root results, pinned definitions, process-concurrent decision creation, recovery and real process kills during migration and decision transactions. They exercise 10,000 pure evaluations and 1,000 persisted decisions without treating these checks as a benchmark. The real v0.1.2 fixture is upgraded through generation cutover and schemas 6, 7 and 8; pre-migration events do not receive fabricated decisions. Schema 9 is rejected. Real Agent execution and the formal user database were not used. npm audit reported zero vulnerabilities.

The full suite, formatting, typecheck and build results are reported with their actual execution outcomes in the final handoff. Windows Runtime coverage is the existing automated suite, not proof of an actual reboot or logon cycle.

Final regression in the destination repository: 29 test files, 328 passed, 0 failed, 0 skipped. Format check, typecheck and build passed. The isolated npm audit reported zero vulnerabilities. Tests include the decision-transaction process-kill scenario; no real Agent or formal Runtime was used.
