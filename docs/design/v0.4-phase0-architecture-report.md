# TaskCircuit v0.4 Phase 0 architecture report

The audit used the released v0.3.0 commit `89f1d2a790fb1f7c6f8d9c7a3e73c06cf677bd48`. Package version is 0.3.0, SQLite schema is 10, Plugin API is 1, and declarative schema is 1. The [Automation Ecosystem design](v0.4-automation-ecosystem.md) defines the proposed v0.4 behavior.

## Released implementation

| Area                                 | Released code and behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source interface and lifecycle       | [plugins/types.ts](../../src/plugins/types.ts) requires synchronous `SourcePlugin.ingest(input)`, returning both the normalized envelope and a `TrustedSource`. It has no start, stop, poll, watch, health, or per-instance factory. [plugins/registry.ts](../../src/plugins/registry.ts) stores implementations by kind and manifest ID, checks API version and rejects duplicate IDs within a kind. Registration alone provides no ingress binding.                                                                                                             |
| Source composition and identity      | [plugins/builtin/sources.ts](../../src/plugins/builtin/sources.ts) fixes identity to `local-cli` and trust to `trusted_local_cli`. [cli.ts](../../src/cli.ts) registers built-ins and loads declared Hub plugins before listening, then passes `sourceId: "local"` to `createHub`. [hub.ts](../../src/hub.ts) resolves one Source from that binding. An external Source can register and can be injected by a host/test, but released CLI configuration does not activate it. The passive interface trusts the code supplying `sourceContext`.                    |
| Event intake                         | [hub.ts](../../src/hub.ts) routes loopback-only `POST /api/events/v2` through the selected Source and then `ingestEvent`, with a 131,072-byte request limit. It returns conflicts before calling `processDecisions`, and otherwise invokes Decision and materialization processing after intake. The scheduler and legacy `POST /api/events` use the separate `createEvent` path. [scheduling.ts](../../src/scheduling.ts) defines retry delay, cron and instant parsing.                                                                                         |
| Durable event identity               | [event-core.ts](../../src/event-core.ts) validates context separately from the envelope and caps canonical payload at 65,536 UTF-8 bytes. In a SQLite transaction it identifies deliveries by `sourceInstance` and `sourceEventId`, compares the canonical digest, and persists Event, delivery history and Root links. A matching replay returns the original receipt, a changed digest records conflict, and a valid event without a target persists as unroutable. The digest includes Automation IDs, trust context, correlation and other normalized fields. |
| Routing and authorization            | [config.ts](../../src/config.ts) validates Agent IDs, distinct Source/type route pairs, Channel instance IDs and schedule references. [declarative.ts](../../src/declarative.ts) accepts only `when.source: "local"` with a unique trusted route and matching Agent, and pins `local-cli` / `trusted_local_cli` in the immutable snapshot. [policy-core.ts](../../src/policy-core.ts) checks pinned source identity, trust, Agent profile, workspace and capability constraints. Registering an external Source alone cannot route an applied rule.               |
| Channel composition                  | [plugins/types.ts](../../src/plugins/types.ts) defines `createChannel({ id })`. [plugins/builtin/channels.ts](../../src/plugins/builtin/channels.ts) registers `local-console`. `config.channels` maps configured instance IDs to implementation types. [hub.ts](../../src/hub.ts) resolves those types through the Registry at construction, passing only the instance ID. [notifications.ts](../../src/notifications.ts) defines delivery input and the current `{ ok: boolean }` result. The test injection seam bypasses Registry composition by design.      |
| Notification persistence and retries | `createNotification` and `dispatchNotifications` in [hub.ts](../../src/hub.ts) use durable notification and delivery rows, choose configured Channels by instance ID and resolve or cancel deliveries on state changes. The dispatcher claims with a 30-second lease, fences completion by token and expiry, delays a failed attempt by five seconds, and exhausts after three attempts. Completion notices require `notifyOnCompleted`. Delivery can be repeated if the remote effect succeeds before TaskCircuit records the receipt.                           |
| External loading                     | [plugins/loader.ts](../../src/plugins/loader.ts) accepts explicit trusted config declarations. The Hub loads Source/Channel modules, and the Worker loads Agent modules before claiming. Paths may be local absolute, relative to the config, or installed packages resolved from that location. Dynamic import executes top-level code before validation. The synchronous default factory, matching manifest ID and kind, kind-specific method and Registry API checks all apply.                                                                                |
| Startup, shutdown and health         | [cli.ts](../../src/cli.ts) binds management to `127.0.0.1` and closes the Hub on signal or launcher IPC. Hub hooks manage dispatcher, streams, scheduler, Decision recovery and SQLite. `/api/health` reports Hub availability and Doctor has runtime probes. There is no Source lifecycle or per-integration health. [Windows launcher](../../src/platform/windows/launcher.ts) gives the Hub two seconds to exit during coordinated shutdown.                                                                                                                   |

## Design decisions and integration work

- **Phase 1 requires Source API 2 for lifecycle.** API 1 is the released compatibility contract. The v0.4 Host supports Source API 1 and 2, and Agent and Channel API 1. The Hub binds each active Source instance to its own submission callback and configuration. Routes name the configured instance, while plugin declarations name the implementation. Required Source startup failure aborts Hub startup.
- **Phase 2 separates ingress from management.** One Hub-owned dedicated listener binds loopback on its own port. The operator terminates HTTPS and forwards only registered webhook paths. Generic webhook authentication is HMAC-SHA256 over the raw bytes before JSON parsing. `X-TaskCircuit-Delivery` or a configured equivalent supplies a stable delivery ID. The Hub binds the identity, classifies external payloads as data and picks the trusted route. Acknowledgment follows durable acceptance or verified deduplication.
- **The routing gap belongs outside Event Core.** Extend trusted instance/route config and existing declarative validation to select and pin an external instance. Keep the existing Event transaction, policy and recovery path. Reuse existing durable Root links to reconstruct prior route authority for duplicate checks. Characterize the replay and storage assumption with tests before finalizing Phase 2.
- **Phase 3 is webhook-only GitHub intake.** Accept `issues.opened` and issue-only `issue_comment.created` with stable GitHub delivery IDs. Defer PAT/App provisioning, polling and write-back. A GitHub comment is distinct from an authenticated human answer.
- **Phase 4 adds outbound Feishu notifications.** Keep Channel delivery and retries with the existing dispatcher, and keep answers in Inbox/Answer. The webhook URL and signing key are Hub environment references. Verify redaction, delivery timeout and credential isolation from Agent launch paths, including Windows.
- **Phases 5–7 deliver templates, setup and evidence.** Ship copyable rules files and use the current apply path. Use Doctor for sanitized per-instance health. The flagship RC test is GitHub Issue → TaskCircuit → Codex → Feishu, with credential-free fixtures in CI and opt-in real service checks for the RC.

The existing scope supports the Phase 0–7 sequence. Schema 10 remains the design target. A migration proposal is necessary only if a later phase proves a need for additional durable state. The design relies on the Trusted Local plugin model and makes no exactly-once guarantee for external effects.

## Review scope

The branch `v0.4-dev` was created and pushed at the released baseline. The Phase 0 commit covers the two design documents and the public roadmap. The corrected compatibility matrix and instance identity model were reviewed before Phase 1. The regression gate is format check, typecheck, full tests, build and npm audit on the target checkout. Git checks cover whitespace, expected file scope, matching baseline refs and the unchanged LOCAL_ONLY hash.

## Validation results

- Target checkout on Windows with Node 24: typecheck and build passed. All 474 tests passed in 53 files, with zero failures or skips. The dependency audit found zero vulnerabilities.
- The direct format check flagged 39 unchanged baseline files with CRLF in the Windows working tree. The same command passed on an isolated copy of the release baseline plus the three final Phase 0 documents, using the LF settings from Windows CI.
- Git whitespace check passed. The only tracked diff is the roadmap. The two new design documents are untracked, along with the unchanged LOCAL_ONLY document. Local and remote main, local and remote v0.4-dev, and the release tag all resolve to the baseline commit.
