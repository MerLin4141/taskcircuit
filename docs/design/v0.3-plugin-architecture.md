# TaskCircuit v0.3 Plugin Architecture Freeze

Status: **design freeze for v0.3 planning; not implemented**. Baseline: v0.2.0 (`1586801ceb423348372442b91156df4e31015e9c`). The proposed interfaces and commands below are contracts for future work, not current APIs. Agent = intelligence; TaskCircuit = control. The user model remains Automation → Event → Root → Agent.

## Goals

Introduce small explicit Source, Agent and Channel boundaries and one registry per process. Adding an implementation must not require changing Event Core, Worker dispatch, or notification dispatch respectively. Built-ins use the same registration and lookup as external plugins. Keep v0.2 durable scheduling, policy, fencing, cancellation, feedback and result confirmation intact.

## Non-goals

No marketplace, download or automatic install, plugin host/IPC, dependency graph, DI/IOC framework, generic event bus, worker protocol or database rewrite. No full GitHub/GitLab source or chat ecosystem, remote worker, cloud, multi-user/RBAC, OS sandbox, approval workflow, Action Plugin/outbox, exactly-once side effects, complex policy DSL, or token/cost budget. v0.4 is the prospective ecosystem stage, not a delivery commitment.

## Plugin kinds and contracts

These are conceptual TypeScript shapes; exact exported names and serialization are Phase 1 design work. No plugin is granted a database handle, Hub lifecycle writer, or Core transaction through these APIs. This is an API boundary, not security confinement of trusted code.

### Source Plugin

A Source instance is configured by trusted local configuration and runs in the Hub. Its lifecycle starts/stops an integration and submits normalized events via an injected narrow event submission callback. A callback accepts an event identity, type, data and optional correlation/time fields; the host supplies its configured source instance and trust context. The plugin cannot choose another source identity or assert internal/feedback trust. The host validates routing, Automation association, limits and duplicate identity before ingestion; an accepted event means local durable acceptance, not exactly-once upstream delivery. On redelivery the same stable source event ID must be reused with the same content; conflicts are reported, never silently overwritten. Payloads remain untrusted, including fields suggesting an Automation, executable, workspace, capability, max runs or deadline. Plugin code must not create Root, Work Item, Decision or Execution through the contract.

Trusted plugin implementation ≠ trusted incoming event payload. `loopback != authentication`: do not treat loopback, source display names or plugin IDs as proof of caller identity. Local CLI compatibility is preserved, while external source trust binding and isolation require implementation tests before claims of authentication.

### Agent Plugin

Runs in the Worker and exposes an asynchronous execution method taking the existing `AgentExecutionInput` fields: Work Item and Execution identity, working directory, trusted instruction, event context as data, previous human answers, optional external session ID and model, plus retry/sequence metadata where needed, and an `AbortSignal`. A fresh run has no session ID; resume supplies the previously persisted one. It returns normalized `AgentResult` or an existing structured agent error. The host validates results and keeps session persistence, lease fencing, heartbeat, result receipt/reconciliation and lifecycle transitions under Core control. The current wire types are `completed`, `continue`, `needs_input`, `later`, `failed`, `stop`, corresponding to Complete, Continue, NeedsInput, Later, Failed, Stop; plugins do not define Root states. Cancellation requests process termination but cannot retract external effects. Passing untrusted event context as data does not guarantee an LLM ignores prompt injection.

### Channel Plugin

Runs in the Hub and implements the existing delivery concept: delivery/notification ID and human-facing kind, severity, title, body and optional interaction reference in; an explicit success/failure result out. Host-owned persisted notification deliveries, bounded retry, lease and status remain authoritative. Channel failure must not roll back or rewrite an already committed Agent result: result commit ≠ notification delivery. Delivery may be repeated after an uncertain outcome; no exactly-once external delivery is promised. No approval, routing, agent dispatch or Root mutation is exposed by this interface.

## Manifest and API versioning

Minimal manifest: `{ id: string, kind: "source" | "agent" | "channel", apiVersion: 1, version: string }`. `id` is a stable nonempty identifier scoped to its kind; instance IDs are separate from implementation IDs. `version` identifies a plugin release; it is not a negotiated dependency range. `PLUGIN_API_VERSION = 1` is independent of TaskCircuit package version. A TaskCircuit patch/minor does not itself imply an API break. Reject missing/invalid manifests, an unsupported exact API version, and duplicate `(kind,id)` across built-in and external registrations before that process serves traffic or claims work. No signature, remote metadata or compatibility negotiation in v0.3.

## Registry and loading

Each process builds one small explicit `PluginRegistry` with `getSource(id)`, `getAgent(id)` and `getChannel(id)`; names are conceptual. It registers built-ins and configured external plugins through identical validation and lookup, with no builtin bypass or silent overrides. Hub initializes its Source and Channel implementations; Worker initializes Agent implementations. The trusted config identifies which modules each process needs. An unknown referenced implementation, invalid configuration, duplicate ID or incompatible API is a startup error, not a fallback to Mock. CLI doctor may report these failures without claiming a successful runtime start.

External modules are **trusted local executable code**, not a sandbox. v0.3 permits an explicitly configured installed package name or absolute filesystem path, and permits relative paths resolved relative to the trusted configuration file's directory, never the process's arbitrary current directory or an Event. Resolve packages using Node's module resolution anchored to that same config directory; use normal Node-supported local module loading, no URLs, network discovery, installation or update. Missing/ambiguous/invalid configuration and load errors fail startup with a sanitized diagnostic. In particular, loading a module executes its top-level code before an exported manifest can be checked: fail-fast means before serving or claiming, not before executing an untrusted module. Administrators must trust and control the module and its dependencies. Hub and Worker must use the same trusted configuration and compatible installed modules; path and module portability are operator responsibilities. v0.2 with no plugin configuration keeps its built-in behavior.

## Process boundaries and scheduling

Hub owns events, Roots, scheduling, notifications and Source/Channel instances. Worker owns Agent execution and Agent instances. No new plugin-host process or IPC protocol. Keep `tickScheduler` as Core mechanism: cron firing, transactional schedule advancement, Retry, Later and unknown-outcome protection depend on its durable semantics. A future internal/local source adapter may normalize user schedule signals into Event Core, but it must not route Retry/Later through arbitrary external source code or change the legacy path without explicit compatibility tests. A schedule source is not mandatory merely for symmetry.

## Trust and failure model

Host-owned trusted config, never event payload, chooses module/package, executable, workspace, capabilities, max runs and deadline. Snapshot and current policy checks continue to bound execution. Capability metadata is not an OS sandbox; Trusted Local is not isolation from malicious same-user processes or plugin code. External effects are not exactly-once.

At startup distinguish `plugin_load_failed`, `plugin_api_incompatible`, `plugin_not_found`, `plugin_config_invalid` as proposed diagnostics; don't log credentials or paths from payloads. At runtime `source_plugin_failed`, `agent_plugin_failed`, `channel_plugin_failed` may wrap errors, but preserve existing structured `auth_failed`, `quota_exceeded`, `rate_limited`, `agent_timeout`, `agent_protocol`, `agent_execution` classifications. For Agent errors preserve `safeToRetry` and unknown-outcome semantics: a timeout, lease loss, crash or uncertain cancellation is not evidence of safe retry. Source failure must not falsely acknowledge an uncommitted event. Channel failure updates delivery state without changing committed results. No plugin may be able to mark uncertain external actions as safely retriable merely by providing an unverified claim; host applies existing evidence rules.

## Built-in migration strategy

1. Introduce contracts and registry without changing runtime behavior; register Mock, Codex, Claude and local-console in it. Bind local source through the same registry when the compatible source lifecycle exists. Preserve current public identifiers and config.
2. Replace dispatch and the Mock special cases with explicit plugin input/setup contracts; no `if codex/claude/mock` in the dispatch core. Maintain `demo.loop` behavior and existing process/error tests.
3. Add trusted explicit local module loading and lifecycle validation; then bind Source and Channel implementations without weakening delivery or trust boundaries. Schedule stays Core-owned.
4. Add explicit declarative apply separately after the registry foundation, preserving existing commands and pinned snapshots. This sequence describes future work, not completed implementation.

## Config UX and declarative rule compilation

Recommend explicit `taskcircuit apply <config>` (option B), not implicit database writes at Hub startup. Treat a rule file as trusted operator input. Compile and validate the complete plan before applying; unchanged canonical definitions create no new version; changed definitions create new immutable versions and only new Roots pick them up. Reject invalid references, ambiguous source matches and incomplete policy; report all changes, never silently delete absent Automations. The transaction must prevent a partial apply of database changes. Local config files and the database cannot be made one atomic transaction; v0.3 must define and test a preflight/activation protocol rather than promise cross-resource atomicity. See [config UX](v0.3-config-ux.md).

## Backward compatibility

Keep v0.2 `automation create/list/show`, `event emit`, `root list/show`, `inbox`, `answer`, `watch`, `doctor`, `runtime` and existing configuration accepted. Preserve built-in names, session reuse, scheduler timing, Result Receipts, P0 uncertain outcome and P1 reconciliation, leases and cancellation. New plugin API is additive; any existing CLI/API semantic change needs explicit compatibility review and tests. Existing persisted Roots remain pinned to their original definition versions; running work is not implicitly rewritten by apply.

## Migration impact

Phase 0 creates no schema and recommends no Migration 11. Existing trusted config and immutable definition snapshots are the first choice; do not persist plugin loading paths in event data or automatically reinterpret old snapshots. Whether existing tables can express every future apply ownership/versioning guarantee must be verified against real v0.2 upgrade fixtures before implementation. If a durable invariant cannot be met, stop and propose a migration separately rather than silently adding one or claiming schema suffices.

## Open questions

- Exact public TypeScript export packaging and module format compatibility; preserve the frozen resolution and fail-fast rules.
- Atomic apply ownership/idempotency and mapping of rule IDs to existing definition versions without introducing a parallel authority.
- Existing legacy scheduler-to-event behavior versus optional v2 internal-source bridge; first prove behavior and preserve compatibility.
- Plugin shutdown deadlines and diagnostics; cancellation is best effort and cannot enforce untrusted code confinement.
- Whether any additional trusted adapter evidence is needed to attest a start failure is safe to retry; never delegate the policy decision to untrusted payload.

## Frozen decisions

Three kinds, API version 1, shared per-process registry with built-ins on the same path; Hub owns Source/Channel and Worker owns Agent; trusted explicit local modules only; no remote acquisition; Core scheduler retained; explicit apply recommended; v0.2 compatibility and uncertainty safeguards required; no migration in Phase 0. The conceptual interface names are not a published SDK until implemented and compatibility-tested.

## Phase 1 acceptance criteria

- Source/Agent/Channel manifest and kind-scoped registry reject duplicate IDs, missing dependencies and incompatible versions before traffic/claims; builtin and fixture plugins follow the same path.
- Add one local fake implementation of each kind via trusted configuration without modifying Event Core, Worker dispatch or notification dispatch; no external service or production runtime required. Prove missing modules and bad versions fail closed.
- Test event identity/dedup, forged source and payload routing attempts, trusted policy boundaries, old config/CLI, session resume, six feedback forms, cancellation and unknown outcome, result reconciliation, notification failure and scheduler Retry/Later. Include a v0.2 historical database fixture and unchanged snapshots.
- Keep file-backed durability/fault injection coverage and all v0.2 regressions. Verify no schema change unless separately approved. Measure neither plugin code trust nor exactly-once effects as security guarantees.
