# TaskCircuit v0.4 Phase 5 — Automation Templates

Phase 4 was committed as `5274d9b7ad687eefaa325d5062e06932077db86b` (`feat: add Feishu notification channel`) and pushed to `origin/v0.4-dev` before Phase 5. Phase 5 is a local worktree change.

## Model and files

Each template is a directly usable schema-1 `automations.json`, a matching `taskcircuit.config.example.json`, and an operator README. Copy the files, edit the trusted identifiers, preview with `taskcircuit apply automations.json --dry-run`, and use the existing apply path. The database stores the resulting Automation and version records through that path.

- [GitHub Issue Fixer](../../examples/templates/github-issue-fixer/README.md) uses `github.issue.opened`, the Codex profile `codex-main`, a project checkout, and eight runs over two hours. Issue comments are an optional advanced route.
- [Webhook Task Runner](../../examples/templates/webhook-task-runner/README.md) uses `webhook.task`, the Claude profile `claude-main`, a task workspace, and six runs over one hour.
- The [template guide](../automation-templates.md) explains setup, ID matching, versioning and optional Feishu. Local-console is the default for both templates. The guide shows how to add the outbound Feishu Channel with two environment references.
- Both repository READMEs link to the templates. The Phase 5 test suite lives in [automation-templates.test.ts](../../tests/automation-templates.test.ts).

## Evidence

The four template tests load the shipped configs with temporary workspace paths and run the unmodified rule files through the real CLI against isolated Hub databases. Dry-run preserves the complete definition, version and change-feed snapshots. First apply creates a definition and its first version. Identical reapply leaves those snapshots unchanged.

Signed loopback requests create Roots for both templates. The tests check the trusted Agent profile and adapter, workspace, capabilities, max runs, deadline, and local notification settings. Extra payload selectors have no authority over those fields or the plugin and executable. GitHub's projection drops the extra top-level fields and keeps Issue body text as context. Generic Webhook keeps the fields as `external_untrusted` context. The tests also apply an edited rule and confirm the original Root stays on version 1 while the next Root starts on version 2.

The two separate CLI smoke runs started real Hub and Worker processes in temporary homes with Mock adapters under the template profile IDs. Each signed POST returned 202, created one Root for the expected Automation and workspace, and completed after one local Inbox answer and two runs. Both completion notifications reached the local-console Channel.

The full Windows suite passed **543 tests in 58 files**, with zero failures and skips. Typecheck and build passed. npm audit found zero vulnerabilities. The Phase 5 files pass Prettier, and the whole candidate passes the same format check over the LF baseline. The Windows checkout reports only pre-existing CRLF formatting differences in untouched files.

## Boundaries

The GitHub example directs the Agent to leave commits, pushes, publishing and GitHub write-back to the operator. The Webhook example keeps payload instructions inside the existing external context boundary. Trusted Local runs with the local user's OS permissions. Feishu is outbound only and human answers use the local CLI. The test runs use synthetic inputs and temporary workspaces. Public GitHub delivery, real Feishu receipt and authenticated Codex or Claude execution remain RC validation.

Package version `0.3.0`, database Schema `10`, and declarative Schema `1` remain in place. Runtime source changes, migrations, Plugin API changes, and new commands were unnecessary. Source API 1/2, Agent API 1, and Channel API 1/2 remain supported. The local comparison document remained untracked and byte-identical.
