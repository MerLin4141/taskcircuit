# TaskCircuit v0.2 — Scope Simplification and Complexity Audit

> Phase 3.5 design decision, not an implementation or a claim that the autonomous loop already works. This addendum supersedes conflicting forward-looking scope in the Phase 0 freeze; historical decisions and implementation reports remain intact. See [freeze addendum](v0.2-architecture-freeze.md#architecture-freeze-addendum--scope-simplification) and [implementation plan](v0.2-implementation-plan.md).

## Purpose and product boundary

v0.2 aims to be an understandable durable autonomous Agent loop, not a complete enterprise control plane. A normal user needs Automation, Event, Root and Agent: an Automation defines what to do, an Event starts or correlates a Root, the Root is one run of the automation, and the Agent carries out its work. Inbox is the existing place for human questions. Work Item, Execution, Decision, Interaction and Session remain available for advanced diagnostics; they are not separate steps the user must create or manage.

Target flow (not yet implemented): define Automation → Event → Root → internal decision → Work Item → Execution → Agent → feedback → continue, wait or stop. Automation Definition Version is the configuration entry point. Its trusted snapshot plus built-in rules form policy; no separate Policy product, policy scripting, DSL or approval manager is in scope. Decision remains an immutable internal authorization/audit fact recording the pinned policy version, trusted agent/workspace/capabilities, reason and recovery identity. It does not itself orchestrate the user workflow. Generation 2 schema 8 and Migration 8 remain intact.

## Current implementation evidence and reuse

- `src/domain.ts` defines Agent results `completed`, `needs_input`, `later`, and `failed`; it does **not** currently define a loop-level Continue or Stop. `src/agents/protocol.ts` and adapters need compatibility work before such feedback can be used.
- `src/hub.ts` result handling persists an Interaction for `needs_input`; the answer route creates a successor Execution for the same Work Item and session. Later creates a Work Item-owned Schedule, whose firing creates a successor using its parent's session; ownership preserves the Root through the Work Item. `tests/scheduling.test.ts` covers Later/restart/session in existing flows; these are reusable mechanisms, not an already verified autonomous loop.
- `src/hub.ts` scheduler excludes blocked and terminal Roots and prevents unsafe retry for unknown outcomes. `src/automation-domain.ts` projects unknown to blocked and the claim query excludes active/unknown siblings. Preserve `execution_outcome_unknown`, fencing and result receipts; neither local process termination nor a receipt proves external effects were reversed or exactly once.
- `src/decision-core.ts` persists per Event+Root+generation decisions; an authorized plan currently records an existing Work Item or creation intent and creates no Execution. `src/policy-core.ts` blocks invalid profile, workspace and capability selections. Do not turn these internal facts into user-managed objects.
- `src/automation-domain.ts` explicitly rejects Root-wide cancellation (`root_cancel_not_supported`); Work Item cancellation and Abort propagation are existing narrower paths. Future Root cancellation needs design and tests, not a claim of present support. `src/cli.ts` currently provides Event, inbox and answer commands but not the proposed Automation/Root command family.
- No budget reservation/settlement tables were found in the current migrations and domain code. No new budget tables are needed just to carry the simplified product concept, but the actual schema decision remains subject to concurrency and crash evidence.

## Minimal feedback and loop limits

Proposed feedback set: **Complete, Continue, NeedsInput, Later, Failed, Stop**. Continue is an untrusted suggestion: the Hub performs internal authorization, checks Root state and limits, and commits the next Execution idempotently. An Agent never recursively starts itself or grants itself permissions. NeedsInput maps to the existing Interaction/answer flow; Later maps to the existing scheduler and same Work Item/Session/Root when its constraints hold. Retry and waiting/resume remain distinct from Continue, and all Agent starts consume the same Root limit. NeedsApproval, ProposedAction and EmitEvent are deferred; `execution_outcome_unknown` remains a runtime safety state rather than an ordinary retryable Failed feedback.

`max_runs` is a trusted finite positive limit fixed for each Root. Every actual Agent Execution consumes one run, including the initial run, Continue, Retry, Answer and Later resumes. On run 8 of a limit of 8, Continue must not cause run 9. The admission check, Root single-active invariant and durable claim must serialize across workers. Counts may be derived from durable executions only if the implementation can distinguish attempts and crash windows reliably; never equate queued rows with proven starts without an explicit conservative rule. If process creation may have occurred but durable start evidence is missing, count conservatively and block/require verification instead of granting a free attempt. A proven process-start failure may be handled explicitly and safely. If existing data cannot enforce this atomically, propose a minimal Migration 9 rather than claiming a safe in-memory counter.

`deadline` is fixed at Root creation from trusted configuration as an absolute instant. At or after that instant no new Agent process may start, including a Retry, answer or scheduled resume that was queued earlier. Recheck at the actual admission/claim boundary in the same transaction as concurrency and run-limit checks; a simple enqueue-time check is insufficient. Reaching the deadline does not by itself kill an already running Agent: allow it to finish and record its outcome, while denying a subsequent start. Explicit user cancellation and lease-loss handling retain their existing stop behavior, subject to the uncertainty safeguards. Deadline does not undo side effects. Exact terminal projection while an execution is in flight must be specified and tested so a late result and unknown outcome are not overwritten. Both limits must be enforced before an autonomous Continue path is exposed, even if the complete limit UX is Phase 5.

## New-user UX target

A user wants “on `bug.report`, let Codex repair the project up to six runs.” They define an Automation with name, trigger, trusted agent profile, workspace and `max_runs: 6` plus a finite deadline; start the runtime, emit the Event, then watch the Root. They do not configure a decision generation, policy hash, authorized plan or budget reservation. The following names are **proposals**, not current commands or validated syntax:

```text
taskcircuit automation create …
taskcircuit automation list
taskcircuit automation show <id>
taskcircuit event emit bug.report …
taskcircuit root list
taskcircuit root show <id>
taskcircuit inbox
taskcircuit answer <interaction-id> <answer>
taskcircuit status
```

Quick-start target: create Automation → start runtime → emit Event → watch Root. An optional future `decision show` is advanced diagnostics, not a prerequisite. Configuration format and CLI flags remain to be designed. Current `event emit` exists; the automation/root commands above do not yet exist.

## Remaining roadmap

- **Phase 4 — Minimal Feedback Loop:** wire Decision → Work Item → Execution and implement the six outcomes, reusing Interaction and Scheduler; keep the path gated until durable minimal limits are enforced.
- **Phase 5 — Loop Limits:** finish and expose `max_runs`, deadline and a minimal loop breaker with atomic admission and recovery; do not build complex Budget accounting.
- **Phase 6 — Autonomous Loop E2E & UX:** separately authorized real Codex/Claude E2E and CLI experience; verify Continue, Ask, Later, limits, cancellation and unknown.
- **Phase 7 — Release Preparation:** compatibility, docs, checks and review; no Approval, ActionIntent or Outbox.
- **v0.3 (tentative):** Source, Agent and Channel plugin architecture; action plugins depend on demonstrated need.
- **v0.4 (tentative):** ecosystem integrations such as GitHub, Webhook, Slack, Email, CI and monitoring; revisit approval and externally executed actions only with an explicit design and authorization.

These are directional scope labels, not delivery guarantees. Trusted Local does not provide OS-enforced filesystem/network isolation; an Agent running with user privileges may itself perform external writes even though TaskCircuit has no external action dispatcher. The system does not promise external exactly-once effects.
