# TaskCircuit 路线图提案：v0.1.2—v1.0

> 本文件供评审，版本号和顺序均非发布承诺。既有 `docs/roadmap.md` 仍是当前文档；本提案经批准后再同步。基线 v0.1.1 的 SQLite 数据、CLI、API 和真实 Agent 会话应保留；任何不兼容变化需要公布迁移方案与版本策略。

## 边界与依赖

核心拥有：事件接收和持久性、规则判定、关联与幂等、Work Item 状态机、租约调度、预算、交互、决策审计、受控能力授权、Outbox。来源、Agent、通知通道、外部动作、执行后端作为适配器或插件；核心可用 Mock 及本地测试实现启动。带外部写入的自动化依赖来源身份校验、动作权限、人工审批与不确定结果处理；不能为了先接入平台跳过这些门槛。

安全隔离不能等到 v1 才讨论：v0.2 起设计执行边界，并在自动处理不可信输入或授予高风险能力前提供经验证的隔离后端；没有隔离的本地模式清楚标为 Trusted Local。v0.3 以前插件接口可作为内部端口逐步演进，不提前宣称第三方稳定 API。

## v0.1.2 — Core Reliability

- **目标**：弄清和修复现有任务恢复、状态一致性及可观察性的已证实问题；默认行为与旧数据兼容。
- **功能 / 模块**：建立租约、心跳、重复回执、重试和恢复的失败矩阵；诊断和日志补全，明确外部副作用不确定；对有证据的问题做最小修复。保持 Codex、Claude、调度、人工交互和 Windows 后台可用。
- **数据模型**：默认不要求重构；如持久化 unknown 或诊断需要新字段，使用兼容迁移并验证旧库升级，历史不可知字段保持未知。
- **接口**：旧 CLI 和 API 保持；新增诊断字段仅追加，机器可读格式需兼容，状态语义变化须单独评审。
- **测试**：Mock Agent 和持久化集成测试覆盖竞争领取、租约到期、重复结果、进程中断；验证 v0.1.1 数据升级；Windows 子进程清理做隔离测试。真实 Agent 测试按授权单独进行。
- **验收**：已识别的高严重度可靠性缺陷闭环；上述五个崩溃时点中可模拟的场景有明确结果；不能安全确定外部结果时不作“恰好一次”承诺。既有回归通过且数据可读。
- **暂不做**：无限自循环、外部来源生态、稳定插件市场、宣称 OS 沙箱。

## v0.2.0 — Autonomous Loop Core

- **目标**：以 Work Item 为中心提供可解释、有界的事件—判断—执行—反馈循环。
- **功能 / 模块**：统一事件与来源作用域、幂等约束、事件到工作项关联、策略版本快照、结果分类、共享根预算与熔断、决策记录；引入安全的 unknown / 人工核实路径。设计并验证本地隔离后端的基础能力，自动化高风险动作前执行相应隔离和审批门槛。
- **数据模型**：增量引入 EventWorkItem、Decision、RootBudget 和动作意图等记录；在事务中写入接收、决策与调度意图。为旧任务提供兼容映射，不补造历史事件或策略。
- **接口**：新增版本化事件入口和只读解释查询；旧入口继续可用或明确过渡。可信配置提供 Agent、工作区、预算及动作许可；外部 payload 不能更改权限。
- **测试**：相同投递重复和不同内容冲突、不同事件关联、运行中归并、并发领取、预算跨重试/重启继承、审批变更失效、外部结果不明的故障注入；多平台隔离能力分别测试。
- **验收**：并发重放测试中同一来源与投递键只产生一个接收结果；每个执行可追溯事件、决策和策略版本；设置的执行次数、深度和截止时间经重启不可重置；外部不确定动作不会无条件重做。成本数据缺失时不声称费用硬上限。
- **暂不做**：任意第三方插件默认可信、无审批外部写入、全量事件溯源强制迁移。

## v0.3.0 — Plugin Architecture

- **目标**：稳定扩展边界，保留无外部插件即可测试的内核。
- **功能 / 模块**：Source、Agent、Channel、Action 和 Execution Backend 接口；注册、能力声明、版本协商、生命周期、失败和取消；Mock 内建。Policy 先保持内置，第三方策略如引入也只能建议、不能绕过最终授权。
- **数据模型**：插件实例与接口版本、可信配置快照、调用回执和能力版本；不把密钥写入审计事件。
- **接口**：发布最小版本化插件契约、错误分类、测试套件和兼容策略；插件只能经受控 API 请求状态变更。实现上防止直接访问数据库需 OS 层强制隔离，同进程接口声明本身不够。
- **测试**：合约测试覆盖启动、取消、崩溃、超时、重复回执、插件不兼容和 capability 缺失；核心无外部插件测试；隔离后端按系统分别测试越权拒绝。
- **验收**：现有 Mock/Codex/Claude 路径通过适配器契约及回归；无插件下核心可测试；不兼容版本拒绝加载并给出原因；未经授权的能力请求被拒绝。
- **暂不做**：插件市场、默认信任任意插件、把进程接口称为安全沙箱。

## v0.4.0 — Automation Ecosystem

- **目标**：在安全门槛达成后试点有限外部接入和通道，证明完整闭环。
- **功能 / 模块**：优先 GitHub / GitLab 事件来源、通用 webhook 通道；根据需求逐个评估飞书、钉钉、企微、Slack；ACP 或通用 CLI 作为单独 Agent 插件。外部写入需要明确 action 插件、权限、审批、幂等及审计，不等同于 webhook 接入。
- **数据模型**：来源实例、投递去重记录、外部消息 / 动作回执、渠道主体关联与审批记录；为数据保留和删除提供策略。
- **接口**：各平台独立认证、去重 ID、可用事件与版本声明；通道发送与互动回调分开；配置不引入明文凭据。
- **测试**：假 HTTP 服务验证签名、重放、时间乱序、平台故障、重复投递和回执丢失；真实服务测试需明确授权且不向第三方发送未授权消息。
- **验收**：至少一个来源、一个 Agent 和一个通道完成隔离测试中的事件—工作项—人工交互—继续链路；来源伪造和权限升级用例被拒绝；外部写入结果不明可暂停核实。
- **暂不做**：默认生产级多平台覆盖、自动交付所有 PR、未经授权发消息。

## v1.0.0 — 面向生产的自主 Agent Loop 候选

- **目标**：在明确支持的部署环境内，达到可证实的持久性、安全、升级和运维要求；“生产就绪”只适用于通过验收的部署配置。
- **功能 / 模块**：稳定协议与兼容承诺；故障恢复、备份恢复、保留及审计、安装升级、监控、隔离与凭据管理、人工处置机制。多用户或远程 worker 需另行设计，不自动包含。
- **数据模型**：固定模式和兼容约束、可校验备份；历史及插件版本可追溯，保留和删除行为明确。
- **接口**：公开稳定 API、错误与兼容策略、插件版本政策、配置升级说明和运维手册；不对未验证的插件作兼容保证。
- **测试**：跨版本升级/回滚及备份恢复、并发和长时间故障注入、预算及安全边界、支持平台兼容矩阵、真实 Agent 与交互式系统测试；须有可复现环境、测试记录及审批。
- **验收**：已声明支持矩阵的全部强制检查通过；重复投递、过期租约、五个崩溃边界和审批失效测试均通过；恢复演练验证数据一致；外部副作用 unknown 有运行手册；所有高严重度已知缺陷解决或明确阻断发布。性能、可用性和恢复目标在部署基线明确后量化，不能由本文虚构数字。
- **暂不做**：无证据的“绝不丢任务 / 恰好一次”、对所有 Agent 及操作系统的全面兼容承诺。

## 待决策问题

1. 业务关联键由哪些可信解析器提供？跨仓库、跨来源和已完成任务重开如何授权？
2. 事件和决策日志保留多久、如何处理敏感资料与删除请求？是否需要完整事件溯源？
3. Agent 会话失联后，哪些平台可可靠查询外部动作与用量，哪些必须人工核实？
4. Windows、Linux、macOS 各自的隔离执行边界、可用身份、网络控制与验收环境是什么？
5. 审批主体如何认证，离线回复如何绑定原消息，授权撤销如何生效？
6. 根预算单位和默认值是什么，成本不可测时如何约束；谁能调整？
7. 规则版本变更后待执行任务采用旧快照还是新配置？需要怎样的显式迁移？
8. 新接口与 v0.1.1 API、CLI、数据库和发布说明的兼容期如何确定？

上述问题解决前，不把提案当成已落地能力或发布日期。

v0.2 的 Definition 有单次任务的内置默认值；周期 Definition 每次按稳定触发键产生有界 Root。Root 终态不重开；新事件由规则产生新 Root。迁移不把历史缺失的决策、来源或成本假装为已知。以上都需在动手前审查实际 SQLite 迁移与旧客户端约束。
