# TaskCircuit v0.2 — SQLite Schema Proposal

> 本文同时记录 Phase 1B 已落地的 Domain Foundation 与后续仍属提案的表；基线 `src/migration.ts` 版本 1–4。Migration 5 负责存储代际切换；Migration 6 实现 Definition、Version、Root 和 Work Item ownership。预算仍是后续设计，不在 Migration 6 中伪造或执行。完整状态机见 [ADR](v0.2-architecture-freeze.md) 和 [API](v0.2-api-proposal.md)。所有时间为 UTC；epoch/version 为整数；所有 PK/FK、UNIQUE 和索引须在真实迁移中验证。按照冻结 ADR，Root 可暂时处于 created 且无 WI；手工任务的隐式 Root 与其第一个 WI 必须同事务提交。

## Dedup、状态、预算事务

`BEGIN IMMEDIATE`：验证可信 source instance → 同键查 delivery → 同摘要返回既有 receipt / 异摘要 conflict → 记录 Event、Delivery → 根据已冻结 policy 和稳定 correlation rules 选择 Root/WI → 校验 Root version + deadline + budget → 插入 Decision、reservation、Execution/后继意图和 timeline → COMMIT。Agent/HTTP/通知在事务外。若一个外部 Event 经多个 Definition 匹配，应使用唯一 `(event_id,definition_id)` 约束在 Definition 修订间去重，而不是只在 version 内去重；若策略明确允许多次触发须有可信 distinct trigger instance，不能由 payload 任意指定。

预留 1 execution 和 1 call 在同一事务扣额并写唯一 reservation；启动明确失败且可证明无 Agent 创建，可按策略释放 call reservation，execution attempt 是否记账固定为记 1；结果可信则 settle；不知是否启动或是否产生外部动作则 freeze，不按租约超时释放。deadline 是调度前硬准入，runtime 超限请求取消但不是外部硬停止保证；token/cost UNAVAILABLE（仅记录可信 provider usage，不限额承诺）。

## 旧数据选择与迁移

| 方案                                     | 正确性 / 兼容性                                                  | 复杂度与结论                                                             |
| ---------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------ |
| A 一个共享 synthetic Root                | 多个旧 WI 共享 mutable budget、会话语义和终态，违反隔离。        | 不推荐。                                                                 |
| B `root_id` nullable，legacy 永远无 Root | 起步简单但新旧路径永久分叉；难建立 Root 不变量、查询及回收边界。 | 不推荐长期方案；迁移中可暂时 nullable。                                  |
| C 每个旧 WI 一个 synthetic Root          | 所有 WI 有独立所有权；可保存旧会话/调度/交互/receipt。           | 推荐；新增行数与旧 WI 数相同；历史事件/预算/决策标 unavailable，不虚构。 |

迁移顺序：停 Hub/Worker 和旧写入，安全备份含 WAL/checkpoint 一致快照并演练恢复；`BEGIN IMMEDIATE` 创建定义/版本和表，给每个 WI 生成确定性、稳定映射 `legacy:<old-work-id>`（使用独立 ID 命名空间与冲突检查），按当前事实推断 Root 状态；旧 running 或不确定但尚未核实标 blocked，保留原 Execution/lease/error，禁止自动重做；原有 completed/failed/cancelled 与等待状态如实映射，保留 schedule；填 FK、重建约束、核对行数/FK/历史哈希和唯一性，再标 version 6/COMMIT。中断整事务回滚，重启重试可幂等。大库先测临时空间与独占时长，不承诺在线大表迁移；如需分批则先设计持久 checkpoint 和新旧写入隔离。现有 v0.1.2 的 `migrate()` 只检查 1–4 是否存在，不会因为数据库含 version 5 自动拒绝启动；不能声称历史二进制能自行 fail closed。通过 Generation 1 持久隔离、SQLite 写屏障和 Generation 2 独立路径切换；无法排除活动或不确定执行时拒绝切换。实现与限制见 [存储切换设计](v0.2-storage-generation-cutover.md)。新版本应拒绝其不理解的未来 schema；禁止多版本混写，且须实测旧二进制在隔离环境中的真实行为。新版本可保留旧 API 格式，但这不等于旧二进制安全可写。回滚仅靠维护窗口恢复迁移前备份，备份之后的写入需导出/人工重放，否则丢失；不声称双向无损降级。

## Phase 2 实施说明（Migration 7）

Migration 7 只作用于 Generation 2 的 Schema 6，并在单一 SQLite 事务内升级到 Schema 7；Generation 1 不修改。旧 `events` 行保留原字段，新增字段为 NULL，不伪造旧来源身份、投递或 Root 链接。

- `events` 增加 schema version、received/occurred time、payload digest、可信 source instance、parent、trust context 和 correlation key；新事件的身份及 payload 通过触发器保持不可变。
- `event_deliveries` 按 `(source_instance, source_event_id)` 唯一；同身份同规范化摘要读回，摘要不同产生冲突。`event_delivery_conflicts` 保存无原文的冲突审计；`event_delivery_history` 记录接收、校验、去重、关联、路由、处理、重复或不可路由等状态。
- `event_root_links` 用持久 sequence 排序，一个 Event 可关联不同 Automation 的多个 Root；同一 Event 对同一 Automation 的重复关联被拒绝。Root 的 active correlation 使用部分唯一索引，事务中以 Definition、Version、可信 source instance 和 correlation key 关联。
- 已关联事件的 `processed` 只表示 Event Core 完成持久化和关联，并不表示 Agent 已运行。未注册或未匹配事件根据用户决定持久化为 `unroutable`，不创建 Root；之后相同投递仍返回原 Event，不因路由变化自动重做。无效请求在进入业务事务前拒绝，不保存其原始 payload；事务失败回滚，不保证保存失败诊断。
- v1 payload 使用 JSON 规范化（对象键按 UTF-16 顺序排序、数组保序），规范化 UTF-8 最多 65,536 字节；完整 HTTP 请求上限 131,072 字节。常见凭据字段和可识别凭据形态被拒绝，但该检测不是完整秘密扫描，调用方仍须避免发送凭据。
- 可信内部子事件只能继承经可信执行上下文指定的父 Root；父 Event 关联多个 Root 且上下文未指明来源时拒绝。终态 Root 不重开，同一关联标识的新 Event 创建 successor，前驱按持久插入顺序确定。

这些字段和约束不实现 Policy、Budget、Agent 自动执行、插件或外部集成；执行副作用不在本阶段范围。

## Phase 3 implementation: Decision persistence (schema 8)

Migration 8 runs only after generation 2 has reached schema 7. `decisions` stores one immutable fact for each `(event_id, root_id, evaluation_generation)`, ordered by its local SQLite sequence. `decision_requests` binds a caller's stable request ID and canonical request digest to that fact. Updates and deletes are rejected. `decision_runtime` records the highest pre-migration event-link sequence: historical events are not retroactively described as having had decisions. No generation-1 data is migrated in place. The migration and its schema marker are committed atomically.

A decision records the pinned definition version, built-in policy version plus canonical snapshot SHA-256, trusted configuration SHA-256, root revision, type, reason, capability set, and optional immutable plan and digest. The SHA-256 canonicalization is shared with result receipts. New evaluations require a distinct positive generation; replaying an identical request returns the original decision. No evaluation materializes a Work Item or starts an Execution. An authorization can record an existing Work Item or a `create_work_item` intent.

## Phase 4 candidate — generation 2 schema 9

Migration 9 creates `decision_materializations`, with an immutable primary-keyed `decision_id` and references to the corresponding Work Item and queued Execution. The relation is committed in the same SQLite transaction as the initial Work Item and Execution. Legacy/manual rows need no fabricated origin. `root_status_projection` also accounts for authorized Decisions that have not yet materialized. The migration is generation 2 only, transactional, and leaves historical feedback untouched. The version guard rejects schema 10. See the Phase 4 report for actual validation and limitations.

Continue and Stop reuse the existing Execution result and result-submission receipt: Continue records structured output and leaves the Work Item waiting with no automatically created successor; Stop records a completed Execution and a cancelled Work Item, without retrying or cancelling the entire Root. The separate Phase 5 limit gate is not implemented and automatic Agent claims for automation Roots remain closed.

## Phase 5 — generation 2 schema 10

Migration 10 freezes `max_runs` and UTC `deadline_at` on automation Roots and adds a unique `continue` successor index keyed by parent Execution. Required-value and immutability guards prevent changing a Root's limits or mode; legacy/manual Roots keep NULL limits. Existing schema 9 automation Roots are populated from their pinned Definition snapshot and trusted `created_at`, with finite defaults applied as a migration policy when no limits were configured. See [Migration 10](v0.2-migration10-report.md) for transaction and rollback boundaries.
