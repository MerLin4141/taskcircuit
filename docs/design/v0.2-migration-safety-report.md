# TaskCircuit v0.2 — Migration Safety Gate 0 报告

## 结论

**Old binary future-schema rejection: NOT PRESENT。Upgrade exclusivity: UNSOLVED。** 实际 v0.1.2 可以继续打开、读取和写入一个 `schema_migrations` 最大版本标记为 5 的测试副本；只检查现有 Launcher 状态及某个端口不能证明没有独立 Hub/Worker，也不能防止检查之后旧进程再启动。按 Phase 1 停止条件，本轮没有实施 Migration 5 或将其接入生产启动路径。

**Operational upgrade requirement:** 在任何未来的 Migration 5 之前，v0.1.2 Hub、Worker、Scheduler 和 Runtime Launcher MUST 全部停止，并在整个迁移以及新版访问期内由可信的外部维护措施阻止旧版本恢复写入；这些措施目前尚未实现或验证。不要将该要求误写成现有代码能自动保证的能力。

## 真实旧版本实验

- 代码来源：本地 `v0.1.2` annotated tag 解引用提交 `2652ca100bb37abf79b75618cc6991e00721e897`，用 `git archive` 提取到独立临时工作区，再从该快照源码 `npm run build`。没有 checkout、覆盖或修改正式工作区；依赖使用本地现有依赖目录。
- 数据：单独创建临时 Home 和 SQLite 数据库。旧 Hub 正常初始化后读到 `MAX(schema_migrations.version)=4`；构造 Work Item 和 once Schedule，关闭 Hub，然后只在该副本中插入 version 5 标记。**这不是实际 Migration 5，也不代表已验证 v5 表结构兼容。**
- 旧版 v0.1.2 重新打开模拟 version 5 的库：Hub **启动**；连接到该临时 Hub 的旧版 `status --json` **成功读取**；调用旧版 `workOnce`，使用 Mock Agent **领取并执行**，Execution 进入 waiting_input；推进受控测试时钟后 Scheduler **触发一次**。
- 在独立 Hub 对同一临时库打开期间，另一个旧版 Hub 也能打开并创建测试事件。无 Launcher 元数据时，`readRuntimeStatus` 返回 `stopped`，但受控的 Hub 随机端口实际可连接；另一个无关随机端口检查返回空闲。这证明 Launcher 状态与单个端口的检查不足以穷举所有数据库访问者，不代表我们检查了或改变了用户正式 Runtime。
- 以上结果来自一次隔离执行；旧版无“未来 schema”拒绝在 `src/migration.ts:42-85` 可进一步解释：代码只分别查询 1–4 是否存在，不检查最大版本。`src/cli.ts` 允许单独运行 Hub/Worker；`src/platform/windows/runtime.ts` 的状态基于 Home 的 runtime.json 和命名管道，而非所有潜在 DB 连接。

## 失败情景与边界

检查 Launcher stopped、缺省端口未监听后，独立旧 Hub 可以仍持有数据库连接，也可以在检查后于其他端口或作为库使用者启动。SQLite `BEGIN IMMEDIATE` 能在事务中串行化写入，却不会让不理解 version 5 的旧客户端在提交后拒绝继续写。`worker_presence` 是心跳记录，不是所有 Worker/直接 SQLite 写者的可靠登记；PID、陈旧元数据和固定端口也不是排他凭据。因此，在现有架构中没有证据证明单独的 preflight 能消除旧版本混写和检查到迁移之间的竞态。没有进行正式数据库、正式 Runtime 或旧版 Agent 调用。

## 最小可行后续方案（提案，尚未实施）

1. 首先明确维护边界：可靠地停止并阻止旧 Launcher、计划任务和所有独立 Hub/Worker 的重启；通过受信的外部运维或操作系统访问控制保持排他，直到旧程序不再能打开该库。仅“发现端口未占用”或让新程序持有一个旧版本不遵守的锁不够。
2. 新版本的升级前置检查应 fail closed：无法核实外部排他、状态不明或检查过程中所有权变化就拒绝升级，不能自动 kill/stop 用户 Runtime。对于手动运行的旧二进制，明确哪些部署条件可被证明、哪些只能由人工维护流程保证；未解决之前不得宣称自动独占。
3. 待排他方案获审并实测后，再实现 schema > 5 拒绝、事务内 4→5 迁移、失败回滚、真实旧库保全和中断恢复。备份由操作者在维护期执行并验证，SQLite 事务回滚不等同于防止磁盘或硬件损坏。
4. 在隔离 Windows 测试中覆盖活动 Launcher、独立 Hub 的随机端口、独立 Worker、检查后启动竞态、旧数据库句柄仍打开和旧版本重启。实现和操作权限需另行审核；本轮未更改 Windows 系统或计划任务。

## Phase 1A storage-generation decision

The earlier in-place safety blocker is addressed by separating generation paths, holding a SQLite writer barrier, atomically persisting legacy write-deny triggers and marker, and validating the current store before startup. The migration guard is an OS-released SQLite writer lock. See [cutover design](v0.2-storage-generation-cutover.md) and the isolated `tests/storage-generation.test.ts` evidence. This does not stop an already executing external side effect, nor does it prevent a same-user actor from deliberately altering SQLite files. The cutover refuses potentially active or uncertain executions instead of assuming they stopped. The actual Windows reboot/logon cycle and real agents were not tested.
