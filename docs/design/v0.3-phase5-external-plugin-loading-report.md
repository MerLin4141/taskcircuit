# v0.3 Phase 5 trusted external plugin loading

`src/plugins/loader.ts` loads a single default factory per trusted local declaration and registers its result into the existing process-specific Registry. Hub loads Source/Channel declarations before listening; Worker loads Agent declarations before online presence or claims. Module paths are relative to the config directory, absolute local filesystem paths, or installed package names resolved using Node ESM conditions by a short-lived Node resolution subprocess. URL specifiers, Node builtins, UNC/network paths, automatic downloads and installation are rejected. The resolver process does not execute the plugin; the actual import occurs afterward in the Hub or Worker.

The operator's trusted config declares `id`, `kind`, and `module`; the manifest must match, and invalid versions and duplicate builtins fail Registry validation. Imported module top-level code executes before validation; plugins are trusted local code, not sandboxed. The Source contract supports loading and registration but does not provide active poll/watch lifecycle or automatic endpoint wiring. Exactly-once external side effects are not guaranteed. Doctor plugin diagnostics are deferred.

`tests/plugin-loader.test.ts` checks local resolution, package fixtures, rejection and isolated registry instances. `tests/plugin-runtime-integration.test.ts` runs a local Worker with an external Agent, normal Hub notification delivery/retry via an external Channel, Source registration, and startup ordering with broken plugins. It does not replace real Codex or Claude compatibility validation. No real Agent was run in this phase.

External Agents without a custom workspace preparation hook receive a created working directory; the builtin Mock retains its previous no-op preparation. The execution integration verifies a fresh session; external Agent Continue / resume is not independently verified in this phase.
