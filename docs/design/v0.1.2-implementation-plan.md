# TaskCircuit v0.1.2 可靠性实施计划

> 这是待评审计划，不是已实施变更。输入基线 `4fb7cf13fd7c243c8d2bd82ece34f75ae37a55df`；依据见 [代码审计](v0.1.2-code-audit.md) 和 [故障矩阵](v0.1.2-failure-matrix.md)。P0 为建议的发布阻断级风险；先以假 Agent、临时数据库和受控故障注入写失败测试，再修改实现。

## 目标与范围

修正现有系统在失权、终止和结果确认时可能误重做或丢失判定的问题；保留已有 SQLite 数据、公开接口及可验证的 session 续用。事件接入、Automation Root、Root Budget、完整 Policy Engine、通用 Action Outbox、正式插件契约和 Execution Backend 均不进入此版本。任何风险控制都不承诺外部副作用恰好一次，也不把 Job Object 称为隔离。

## P0：不确定执行的保守恢复

**依据**：[hub.ts](../../src/hub.ts#L933) 重领过期 running；[worker.ts](../../src/worker.ts#L64) 未及时中止失权 Agent；[errors.ts](../../src/agents/errors.ts#L45) 超时可重试；首次 session 提交前未持久化（[hub.ts](../../src/hub.ts#L1075)）。

**建议文件**：

- `src/hub.ts`：区分“确定未启动”与“可能已启动”；不得仅因 lease 过期就对后者再次派发；对超时和无法判断的进程结果避免自动 retry。将处置和工作项状态在事务中一起持久化。
- `src/worker.ts`、`src/adapter.ts`、`src/agents/process.ts`、两个 `src/agents/{codex,claude}/adapter.ts`：引入可取消的执行边界，失权、明确取消、关闭传播取消请求；分清请求停止、确认退出、结果不明，不把中止等同外部回滚。
- `src/agents/errors.ts`：区分已知无执行与可能已执行的超时/异常；正则分类只提供线索，不自动证明安全重试。
- `src/cli-format.ts`、相关读取路径：展示“需核实、可能已经执行”的错误原因，不伪装成普通失败；需要时只做向后兼容的附加字段/错误码。
- `tests/runtime.test.ts`、`tests/scheduling.test.ts`、`tests/agents.test.ts` 及必要的假 CLI fixture：先补可复现故障测试，不调用真实 Agent。

**状态与迁移决策**：优先设计无新增 schema 的兼容方案：对无法证明未启动的过期执行，在原子事务内用现有 `failed` 状态和结构化错误码（例如 `execution_outcome_unknown`）记录“需人工核实”，关联 Work Item 进入既有 failed，并明确它不是“已证实外部失败”。保留原 session、结果、时间和通知。该方案改变旧版“过期自动重领”和部分自动重试语义，属于**行为兼容变化**，必须在实现前确认并提供升级说明；旧客户端只看 failed 时可能忽略细分原因。

如果需要保存跨重启的启动证明、独立 unknown 状态或可审计的人工核实结果，现有 schema / 旧客户端语义可能不足：另提最小 migration 5 和 API/CLI 兼容设计、备份与回滚方案，不能先假定无需迁移。不要通过数据库直接编辑记录或人为补造过去是否启动的事实。

**最低测试用例与验收**：

1. Worker A 领取后、进程启动前和启动后分别强制退出；对于无启动证明的情况，新 Worker 不得盲目重新执行。现有代码无法可靠区分两者，故保守处理可能降低自动恢复率。
2. 假 Agent 将动作写入临时文件后阻塞，注入心跳失权/超时/Worker 死亡；确认没有自动启动第二次，也不把结果称为已撤销。测试直接 Agent 和子进程，不访问真实服务。
3. 两个 Worker 与过期结果并发竞争；旧 token 均被拒绝，数据库事务不留下完成和待重试同时存在的状态。
4. 在外部动作已发生但回执未知时，执行和 Work Item 均保留可诊断的不确定原因；重启后不自动重新调用。
5. 在不涉及 Agent 启动或副作用的可证明场景，验证安全恢复；如无法证明则明确等待核实，不编造启动证据。

**边界**：无法收回已经发送的请求；即使本地杀死进程，外部系统也可能继续处理。人工重做需先由操作者核实。完整可查询/幂等外部 Action 及 reconciliation 属于后续架构，不用 v0.1.2 假装实现。

## P1：取消传播与进程清理

**建议文件**：`src/worker.ts`、`src/adapter.ts`、`src/agents/process.ts`、两种 Agent adapter、`src/cli.ts`；Windows 进程管理必要时检查 `src/platform/windows/launcher.ts`。依据 [hub.ts](../../src/hub.ts#L643)、[cli.ts](../../src/cli.ts#L114)、[process.ts](../../src/agents/process.ts#L64)。

让工作项取消、失权、Worker shutdown 触发可观测中止；如果不增加推送协议，心跳确认失权时可触发，但可能最多延迟一个心跳周期或网络超时，不能称即时取消。为进程清理设计平台差异和超时升级策略；Windows 后台 Job 保护整体 Runtime，单次执行也须测试，前台 Worker 不应假定被 Job 包含。

**测试 / 验收**：临时假 Agent 带子进程，分别测试用户取消、超时、关闭、失权；校验任务状态、父子进程退出及已发生副作用仍被标为需核实；覆盖非受管进程不受影响。进程树管理若不能跨平台可靠实现，明确支持范围，不能承诺已经清理所有后代。

**兼容 / 迁移**：原则上不需 schema；Adapter 接口签名变化是内部调用兼容问题，所有内置及 Mock 适配器一起升级。向现有调用者增加可选 signal 需审查 TypeScript API。

## P1：心跳与结果确认

**建议文件**：`src/worker.ts`、`src/hub.ts`、`tests/runtime.test.ts`、`tests/agents.test.ts`。依据 [worker.ts](../../src/worker.ts#L64) 的永久失败标志和单次提交、[hub.ts](../../src/hub.ts#L990) 的令牌校验。

1. 区分临时连接失败与 Hub 明确拒绝所有权；控制请求超时和同一执行的心跳并发。再次确认持有有效租约前，不可假设仍可安全继续。
2. 对“Hub 已提交但回复丢失”设计结果确认。可先实现受限读取和相同结果的安全确认；若需要持久化请求摘要或确认凭证，则提出最小迁移，不能通过泄露租约令牌或忽略不同摘要解决。
3. 相同结果重复提交不能再次创建 interaction/schedule；不同结果、旧令牌在不符合确认条件时仍冲突。

**测试 / 验收**：一次心跳临时失败再成功、明确 409、心跳请求挂起及乱序完成；提交已持久化后连接中断、相同/不同结果重放、旧 Worker 冒充重放。精确检查响应、Work Item、Execution、session、schedule 和 interaction 数量。

**兼容 / 迁移**：若新增结果确认 endpoint 或允许重复成功响应，评估旧调用方依赖 409 的行为；持久去重摘要可能需要 migration 5 和旧记录缺值处理。不要在本阶段承诺“恰好一次执行”。

## P1：会话、调度与升级回归

**建议文件**：`tests/runtime.test.ts`、`tests/scheduling.test.ts`、`tests/realtime.test.ts`、`tests/windows-runtime.test.ts`，以及如有新迁移的 `src/migration.ts`。依据 [migration.ts](../../src/migration.ts#L3)、[hub.ts](../../src/hub.ts#L675)。

测试已有 session 的 Ask→Answer→Resume、Later、retry 及重启，确保 ID 不变；一次性计划并发 firing 仍只有一条；同时检查 P0 新语义不重做不明执行。用临时旧库覆盖 active、waiting_input、waiting_schedule、已有 session、过期 running 及升级中断；对未证实的外部结果不推断成功或失败。若增加迁移，进行事务回滚、强杀后重开与备份恢复演练，说明从恢复前备份回滚可能丢弃之后写入。

**验收**：原有旧库记录、session 与已解决回答保持一致；不得重复创建计划 firing；对历史 running / 无记录的启动信息一律保守，不编造状态。旧版本与新版本混合写同一数据库的支持与否必须明确。

## P2：Agent CLI 兼容与诊断

**建议文件**：`src/agents/{codex,claude}/adapter.ts`、`src/agents/capability.ts`、`src/agents/errors.ts`、`tests/agents.test.ts`、`tests/agent-errors.test.ts`。补充固定的合成 JSONL/JSON 输出、非零退出、缺失/变更 session、协议异常、额度不足和限流案例，诊断清楚版本或协议不匹配。

**限制**：假 CLI 测试只能证明本项目解析指定样例；真实 Codex / Claude E2E 必须在后续取得明确授权后单独执行。不要在本轮消耗额度或假称当前 CLI 版本已验证。

## 实施顺序与发布门槛

1. 为 P0 编写失败测试，模拟 Agent 已启动但结果未知、续租失效和超时副作用。
2. 决定兼容处置：复用现有状态/错误码，或确有必要时评审 migration 与新增状态；先明确旧客户端和人工核实流程。
3. 实施保守失权与超时处理，再打通取消信号和平台进程清理；确认不能从未知状态自动重做。
4. 补强心跳及重复结果确认；继续保持 stale token 和事务约束。
5. 跑旧库/会话/调度迁移回归与 Windows 临时进程测试；视改动运行完整 typecheck、format 和测试。真实 Agent 及真实 reboot/logon 不因这些测试通过而自动获得验证。
6. 安全审查、记录未验证项目与兼容变化；高风险未知状态未被可靠保守处置则不发布 v0.1.2。

本轮审计已执行的隔离测试和未验证范围详见代码审计；这里的验收均为未来要求，并非已通过的结果。
