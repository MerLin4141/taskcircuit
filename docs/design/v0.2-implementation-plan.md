Legacy manual Work Item APIs and P0/P1 safeguards remain: lease, heartbeat, fencing, result receipts, safe retry, cancellation and `execution_outcome_unknown`. No plan guarantees exactly-once external effects or OS isolation. The existing Work Item cancellation is not Root-wide cancellation. All new behavior needs failure tests first and isolated databases; no real Agent call without separate authorization.

## Phase 4 — Minimal Feedback Loop

Connect an authorized Decision intent to a durable Work Item and Execution, without treating the Decision itself as an execution. Reuse existing Agent Session, Interaction and Scheduler. Add a compatible versioned feedback mapping for Complete, Continue, NeedsInput, Later, Failed and Stop; Continue is only a suggestion, and internal trusted checks authorize every next step. Replaying a result or recovering after a crash must not create multiple successor executions. Preserve the same Root / Work Item / Session for Ask and Later when valid. Avoid a second interaction or delay engine.

**Safety gate:** do not expose or enable autonomous looping until a finite trusted `max_runs` and deadline are durably and atomically enforced for every new Agent start. Phase 4 may build the feedback mechanism behind a disabled path while Phase 5 completes the admission gate; the phase cannot claim a safe runnable autonomous loop until both are present. Handle duplicate feedback, concurrent workers, crash/restart, lost result response, stale lease, blocked/terminal Root, unsafe timeout and malicious capability/profile/workspace suggestions. Enforce one active/unknown-blocked Agent Execution per Root. Continue must never bypass P0/P1 safeguards. Real Agent support is not established by Mock tests.

## Phase 5 — Loop Limits

Implement only trusted finite `max_runs` and a Root-creation deadline, plus a minimal loop breaker where justified. Apply the limit to the first start and all Continue, Retry, Answer and Later resumes. On the last permitted run, another Continue cannot start an Agent. Admission must be atomic across workers and rechecked immediately before start even for earlier queued work; time equal to the deadline is not permitted. Do not terminate an in-flight Agent solely because its Root deadline passes; record its eventual result without permitting another start or overwriting unknown. Explicit cancellation and lease-loss retain their established stop/unknown behavior.

Investigate deriving counts from durable Execution/claim evidence before adding columns; queued rows alone do not prove a process started. If a crash makes a start uncertain, count conservatively and block rather than give a free attempt. Demonstrate transaction behavior for simultaneous final-slot claims, startup failure with proof no process started, crash after process creation, retry/answer/Later, deadline boundary, in-flight result, stale worker and restart. If the current schema cannot represent a correct durable admission, prepare a minimal schema 9 migration proposal and compatibility/crash tests before implementation. Do not add root budget, reservation or settlement tables for their own sake. Max tokens/cost/depth and complex accounting are deferred.

## Phase 6 — Autonomous Loop E2E and UX

Provide the smallest user workflow: configure Automation, start runtime, emit Event, inspect Root. Present Decision and Work Item only as advanced diagnostics; retain existing inbox/answer. Proposed commands, not current capabilities: `automation create/list/show`, `event emit`, `root list/show`, `inbox`, `answer`, `status`; actual syntax remains a later design choice. No Policy create/edit/attach product.

With separately granted authorization, run real Codex and Claude in isolated environments: Event → Root → Continue → next Execution → Complete; Ask → Answer → same session; Later → same session; limits; cancellation; unknown. Record versions, actual results and unverified behavior. Mock results are not evidence of real Agent compatibility. An actual Windows reboot/logon remains unverified unless separately authorized and performed.

## Phase 7 — Release Preparation

Review source, schema upgrade compatibility, documentation, user-facing limitations, all regression gates and security/privacy claims. Release decisions, tags, pushes and public actions require their own authorization. Approval Engine, ActionIntent and Outbox are not v0.2 requirements.

## Later directions and acceptance

v0.3 tentatively addresses Source / Agent / Channel plugins; Action plugins require demonstrated need. v0.4 tentatively addresses integrations such as GitHub, Webhook, Slack, Email, CI and monitoring, with Approval / ActionIntent / Outbox reconsidered only if justified. These are roadmap directions, not commitments.

Acceptance for the eventual v0.2: deterministic trusted authorization; immutable decisions; Event deduplication and per-Root identity; finite loop admission under concurrency and crash; idempotent feedback and recovery; Ask/Later/session compatibility; preservation of fencing and unknown-result protection; safe legacy upgrade; explicit Trusted Local and external-side-effect limitations; end-to-end evidence separated by Mock and real Agent. No release gate is passed merely by this design document.

## Phase 5 implementation record

The Phase 5 implementation uses a central SQLite admission check, fixed per-Root `maxRuns` and deadline, a unique parent-to-Continue relationship, startup recovery and pre-launch lease/authorization checks. The Worker uses the Decision-authorized workspace, and trusted immutable retry configuration is carried into materialized Work Items. Manual and legacy flows keep their prior behavior. See [Phase 5 report](v0.2-phase5-loop-limits-report.md) for measured tests and unresolved boundaries. Phase 6 and release actions remain separate work and are not authorized by this record.
