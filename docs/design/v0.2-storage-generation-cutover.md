# v0.2 Storage Generation Cutover

## Decision and scope

The v0.1.2 tag uses `TASKCIRCUIT_HOME/taskcircuit.db` (schema 4). Its Hub accepts a higher schema and its Worker can claim work; process or port checks cannot prevent a retired binary from reopening the database. In-place Migration 5 was therefore rejected. Generation 2 uses `taskcircuit-gen2.db`, schema 5, with a separate SQLite guard database. The user approved reserving 5 for the storage cutover and using a later Migration 6 for Domain Foundation. No Domain entities are implemented here.

## Cutover and recovery

The v0.2 Hub obtains a SQLite `BEGIN IMMEDIATE` migration guard, then a legacy writer barrier. It rejects running/claimed executions, unknown outcomes and claimed notification deliveries while holding that barrier. It creates and syncs a SQLite backup before any persistent quarantine and verifies its digest for recovery. It builds and checks the new generation from that snapshot. A marker and write-deny triggers for each existing legacy table, including migration metadata, are committed atomically under the barrier. Only then is the validated new database promoted via an exclusive hard link. A missing or damaged pending database after quarantine is rebuilt from the digest-verified backup; damaged pending files are retained. Startup validates both the legacy marker/quarantine and Generation 2 identity. A future schema is rejected with `database_schema_too_new`.

An active old SQLite writer can delay the barrier; a competing v0.2 migration is rejected, not silently unlocked. Existing readers may continue. A v0.1.2 worker must commit its claim before starting an agent and the scheduler persists its firing transactionally; tests exercise the actual archived v0.1.2 build with fake agents. Denial triggers prevent ordinary old writes, not deliberate same-user removal of triggers or changes to database files. The same-user trust boundary remains unchanged.

Crash before quarantine leaves the legacy transaction rolled back; crash after quarantine resumes promotion or rebuilds from backup. This is a one-way cutover: downgrade to v0.1.2 is not supported. Restoring a pre-upgrade backup requires an operator-directed recovery and can discard subsequent Generation 2 changes. Backup and current database are separate; the backup never becomes active. Filesystems without hard-link support fail closed; disk and power-loss durability depend on filesystem guarantees.

The archived v0.1.2 compiled fixture in `tests/fixtures/v012-runtime/` is excluded from formatting. Git EOL normalization is disabled for this directory; the staged blobs were checked against the supplied workspace file bytes. This comparison does not independently establish the provenance of the archive. All tests use isolated temporary homes and fake agents; no formal user database or real Agent is used.
