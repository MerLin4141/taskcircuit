# TaskCircuit v0.4 — Automation Ecosystem

Phase 0 design with Phase 1 lifecycle implemented. See the [Phase 1 implementation report](v0.4-phase1-active-source-report.md) for verified scope. The released baseline is v0.3.0 (`89f1d2a790fb1f7c6f8d9c7a3e73c06cf677bd48`). The [Phase 0 report](v0.4-phase0-architecture-report.md) records which behaviors already exist in that code.

## Product scope

TaskCircuit is a durable automation runtime for autonomous CLI agents. Operators connect a Source, choose an Automation, select a trusted Agent and workspace, apply the rules, and receive results through a Channel.

```text
External system → Source → Event → Automation → Root → Agent
                                                   ↓
                              Channel ← notification ← feedback / human input
```

The flagship demo is **GitHub Issue Auto-Fixer**. An issue opened in an allowlisted repository produces `coding.issue`. The `issue-fixer` Automation runs Codex in a configured local checkout to inspect code, make local changes and run tests. The operator can answer a question using `taskcircuit inbox` and `taskcircuit answer` and resume the same Session. Feishu reports a question, failure, or completion to a configured group. The operator reviews the working tree and decides what to commit or publish. A secondary demo can use a generic webhook, Claude, and local-console or Feishu.

Multi-agent DAGs, supervisors, Agent-to-Agent protocols, remote workers, cloud runtime, multi-user/RBAC, marketplaces, and generic workflow builders are out of scope. The existing SQLite store, Event Core, Root, Execution and Agent Session models carry forward. Action Plugin, outbox, GitHub write-back, automatic commits, pushes and PR creation require separate design.

## Active Source lifecycle and Plugin API

**Active Source lifecycle requires Plugin API 2.** API 1 is the released passive Source, Agent and Channel contract. The v0.4 Host supports Source API 1 and API 2, Agent API 1 and Channel API 1. Agent API 2 and Channel API 2 are outside Phase 1. The v0.3 Host does not understand active lifecycle, host submission or health reporting. Preserve the synchronous loader factory and the passive `ingest(input)` behavior without calling lifecycle hooks on API 1.

The minimum conceptual shape is a factory receiving validated per-instance config and a narrow host capability, a finite asynchronous `start(signal)` that resolves when ready, and optional `stop()` for cleanup beyond cancellation. Monitor later asynchronous work through a sanitized health/failure callback and host-owned transport promises. An instance that runs until abort must signal readiness independently of its long-lived task. Phase 1 implements `createSource(config, host)`, `start(signal)`, and optional `stop()`. Factories construct instances and startup owns resource acquisition. The host receives health transitions without plugin-provided messages. Registration alone runs no instance lifecycle.

The Hub owns lifecycle and installation of signal/IPC shutdown handlers. Validate plugin declarations, instance bindings, route shapes and required environment references before startup. Construct each instance once, allocate one abort controller per instance, and start configured Sources only after the durable ingestion path is usable. Keep the ingress readiness gate closed and withhold runtime readiness until all configured Sources are ready. Source instances are required by default. An explicitly optional Source may fail initialization with an isolated failed status. A factory, bind, readiness or initialization failure closes the gate, aborts and stops already initialized instances, releases listeners and closes the Hub. An absent Source section keeps v0.3 startup behavior.

After readiness, an observed permanent instance failure disables its admission, records a sanitized reason, and leaves independent instances, the Hub and accepted work operational. A transient transport or upstream failure degrades the instance and may recover on the next successful delivery. Neither silence on a push Source nor one rejected request marks it failed. There is no automatic instance restart or polling loop. An operator corrects configuration and restarts after a permanent failure. Arbitrary in-process plugin crashes cannot be isolated by this contract.

On shutdown close admission first, abort instance signals, stop listeners and drain already admitted submissions within one shared bounded grace period. Run optional stop hooks once and reject late submissions even if a hook ignores cancellation. Set the normal Source grace budget at no more than 1.5 seconds for the current Windows launcher's 2-second Hub exit window. Keep SQLite open while admitted transactions settle. On timeout close sockets, record a sanitized diagnostic and let launcher containment handle an unresponsive process. A committed delivery may lose its HTTP response during shutdown and must still be recognized on retry. Phase 1 must exercise signal and launcher IPC shutdown, partial startup rollback, slow hooks and late callbacks.

## Submission, routing and durable acceptance

An active Source receives an instance-bound callback that accepts only `sourceEventId`, `type`, `payload`, and optional `correlationKey` and `occurredAt`. Validate and reject unknown top-level fields at runtime. The Hub derives identity from the configured instance and assigns `external_untrusted` to network submissions, including authenticated ones. Reserve the legacy local identity and internal identities. The callback exposes neither SQLite nor a generic Hub, Worker or routing API. Built-in integration modules use this boundary. Trusted Local third-party code still runs with the user's process authority and has no OS sandbox.

Use one explicit trusted binding per external `(instance, type)`. In runtime config, the route names the allowed Automation and Agent profile. `automations.json` uses the existing `when.source` field for the configured Source instance ID and `when.type` for the normalized event type. Phase 1 provides the trusted route binding and validates the stored source-scoped policy. A later phase will extend declarative compilation additively to provision that policy through `apply`. Check that the current enabled definition matches this binding before supplying its ID to Event Core. The operator provisions routing and applies the rule over the loopback management endpoint. An integration cannot choose an Automation ID, parent Root, Agent, workspace, capabilities, limits, plugin module or executable. Source data never overrides those settings and enters the Agent as context data. Existing `when.source: "local"` retains its current meaning and snapshot.

The Hub calls the existing `ingestEvent` transaction. Decision evaluation and Work Item materialization stay on the existing recovery path and are outside the HTTP acknowledgment budget. For an explicitly allowed event with no route, preserve Event Core's durable `unroutable` outcome. If an explicitly configured route is awaiting a matching applied definition, return a retryable unavailable response and leave the delivery uncommitted. Never fall back to another Automation. During initial setup, apply while management is reachable and before enabling upstream deliveries.

Event Core deduplicates by `(sourceInstance, sourceEventId)` and checks the canonical content digest, which includes the Hub-selected Automation IDs. On redelivery, reuse the original route authority before the digest check. The Hub can read the original delivery and its linked Roots' definition IDs from existing persisted records. A durable unroutable receipt has no target. Compare normalized content through Event Core and never route a replay to a newly selected Automation. The lookup and synchronous submission must be serialized by the owning Hub. Prove replay across restart, route changes, disabling a definition and first admission under contention. Instance IDs, normalization and correlation rules are stable identity inputs. A changed normalized envelope with the same delivery ID produces a conflict for operator review. If existing rows cannot reconstruct an accepted envelope's routing inputs, stop and propose a persistence change rather than silently weakening deduplication.

## Ingress, authentication and secrets

| Design                                                       | Consequences                                                                                                                                                                                              |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Public webhook routes on the existing management listener | Fewer ports, but the socket bind exposes the management surface too. Requires proxy or per-route controls to keep administrative endpoints private and couples ingress shutdown to the management server. |
| B. Separate webhook listener                                 | A separate bind and port isolate the public surface and let admission stop independently. One shared listener is easier to configure and test than one server per plugin instance.                        |

Choose B with **Hub ownership of one dedicated ingress listener**. Sources supply handlers for exact registered `POST /integrations/webhook/<instance>` and `POST /integrations/github/<instance>` paths. They receive no server object or route wildcard. The management listener remains on `127.0.0.1`. Ingress also binds to loopback on an explicitly configured separate port. Public HTTPS terminates at the operator's reverse proxy or tunnel, forwarding only the dedicated ingress paths, preserving the raw body and relevant headers. No wildcard bind or bundled tunnel in the MVP. Both listeners run in the Hub process and use the same lifecycle. Validate route and port collisions at startup and test that public ingress has no management routes.

Require JSON POST, cap raw request bodies at 128 KiB including streamed bodies, and retain Event Core's 65,536-byte canonical payload cap. Reject unsupported encodings and compressed bodies in the MVP. Bound concurrent requests and request reading. Use a total response target under 8 seconds and return a retryable error on saturation or unavailability. SQLite's current 5-second busy timeout and synchronous calls require an explicit ingress contention test. An async timer alone cannot enforce a bound during a blocking database call. Keep the request path free of Decision processing, Agent work and outbound requests.

**Generic webhook authentication is HMAC-SHA256 only.** Validate a single signature header over the original body bytes before JSON parsing, using constant-time comparison after checking the expected format and length. Require a stable delivery ID from `X-TaskCircuit-Delivery` or an explicitly configured equivalent header and use it as `sourceEventId`. Reuse it for retries. Identical bodies can represent distinct events. The raw-body signature does not cover headers, so the HTTPS and forwarding boundary must preserve delivery identity. Validate the configured type mapping and optional correlation field. Bearer authentication and OAuth are deferred. For GitHub verify `X-Hub-Signature-256` with the configured instance secret against the original bytes, then validate the event header, action, and signed payload shape and repository. GitHub headers, including the delivery ID, are not covered by the body signature. Treat the public TLS path and forwarding configuration as part of the deployment trust boundary. Deduplication is scoped delivery handling and does not establish freshness or exactly-once behavior. [GitHub delivery validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) · [GitHub webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)

| Outcome                                                                           | HTTP behavior                                                       |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Durable accepted or unroutable                                                    | 202 after Event Core commits. Acknowledgment describes intake only. |
| Verified duplicate                                                                | 200 after Event Core recognizes the original receipt.               |
| Same delivery ID, different canonical content                                     | 409 with a safe error code.                                         |
| Missing or invalid signature                                                      | 401 with a uniform response.                                        |
| Authenticated but disallowed repository or sender                                 | 403.                                                                |
| Malformed ID, envelope or mapped fields                                           | 400. Too large is 413. Unsupported content type or encoding is 415. |
| Valid GitHub ping or authenticated unselected event/action                        | 204 as an explicit no-op outside Event acceptance.                  |
| Hub not ready, shutting down, route awaiting apply, or transient capacity failure | 503. If the receipt is uncertain, redeliver the same ID.            |
| Unexpected failure before durable acceptance                                      | 500 with a stable code.                                             |

Use trusted runtime configuration with references such as `secretEnv: "TASKCIRCUIT_WEBHOOK_SECRET"`, `webhookUrlEnv: "TASKCIRCUIT_FEISHU_WEBHOOK_URL"` and `signingSecretEnv: "TASKCIRCUIT_FEISHU_SIGNING_SECRET"`. Resolve nonempty values once from the Hub process environment, validate before readiness, and restart to rotate. Use the `TASKCIRCUIT_` namespace and ensure integration values stay out of Worker/Agent environments, including the Windows launcher and external Agent plugin path. The current built-in Agent filtering is useful but does not by itself sanitize the Worker process. Verify launch-from-login provisioning without putting values in task arguments. Store neither values nor credential-bearing URLs in rules, snapshots, events, Root metadata, SQLite, fixtures, docs or logs.

Use allowlisted diagnostic fields such as instance ID, kind, status class and stable error code. Never log headers, signature material, provider response bodies, secret values or webhook URLs. Default errors omit raw event bodies and exception causes. Normalize GitHub payloads to a bounded allowlist. For generic JSON, define the accepted projection and instruct operators to exclude credentials. Event Core's current secret-pattern checks are a backstop rather than comprehensive secret detection.

## GitHub and Feishu

**GitHub Source MVP** supports repository webhooks for `issues.opened` and `issue_comment.created` on issues. Exclude pull-request comments, edits, PR events and polling. Use configured repository IDs, a bounded projection of issue fields and separately enabled routes for each trigger. The flagship uses an operator-controlled demo repository and trusted trigger authors. Use `X-GitHub-Delivery` as `sourceEventId` unchanged on redelivery, and a stable repository/issue key where correlation is enabled. An issue comment is an Event, with no authority to answer an interaction. A matching active Root follows the existing Event and Decision rules. Use repository webhook signatures without a GitHub credential for outbound calls. A PAT adds a credential for outbound API access without improving this push-only flow. A GitHub App adds installation and token management, useful for future multi-repository or scoped API operations. GitHub does not automatically redeliver failed deliveries. Document operator redelivery after outages using the original ID. [GitHub failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)

**Feishu outbound MVP** sends bounded plain-text summaries to an operator-configured group custom bot. Use the environment-provided HTTPS webhook URL, validate the Feishu host and endpoint path, disable redirects, and support the bot's signing secret via environment reference. Use one request per attempt, with a bounded timeout below the lease and a verified Feishu success response as the condition for success. Timeouts, transport errors, HTTP failures and provider failures return a sanitized failure classification or the current `ok: false` result. The Hub owns the 30-second lease, five-second delay and three-attempt cap. The MVP keeps those semantics even for non-transient failures. Abort outstanding sends on shutdown within the Hub's exit budget and let fencing protect late receipts. Completion requires `notifyOnCompleted`. Failure and NeedsInput use existing notifications. Later/Waiting notifications and Feishu interactive answers are deferred. NeedsInput notices direct the user to the existing local Inbox and Answer flow. A future inbound answer requires separate authentication, user/interaction binding and replay handling. [Feishu custom bot documentation](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)

## Configuration, templates and health

Keep trusted integrations in `taskcircuit.config.json`. Module declarations describe implementation IDs. For example, the `github` implementation can run as two independent configured instances, `company-github` and `personal-github`, each with its own trusted settings. A route uses `event.source: "company-github"` to address the instance, while a Channel instance such as `team-feishu` selects `feishu-channel`. Runtime config contains per-instance settings, environment reference names, listener settings, routes, Agent profiles and workspace policies. Preserve the existing Channel `{ type }` instance form and factory's `id`. An additive typed config input can carry validated options for new implementations, while existing instances keep their current input. Rules carry only selectors, Agent and workspace IDs, instruction, loop limits and notification instance IDs.

A conceptual Source configuration is:

```json
{
  "sources": {
    "company-github": {
      "type": "github",
      "required": true,
      "config": { "secretEnv": "TASKCIRCUIT_GITHUB_WEBHOOK_SECRET" }
    }
  }
}
```

The key is the instance ID, `type` is the implementation ID, and `config` is implementation-specific. The built-in `local` instance requires no configuration entry and keeps the existing `local-cli` Event Core identity. The GitHub credential field is for Phase 3.

Ship `local`, `webhook-source`, `github-source`, `local-console` and `feishu-channel` as first-party built-ins through the same Registry. Bundling keeps Git checkout and Windows setup to one install, aligns versions and lets CI exercise the same code that ships. First-party external packages would test independent distribution and reduce core release coupling, but require version matching, distribution and another install path while npm publishing is disabled. Continue exercising external module loading with fixture plugins in CI.

Ship documented, copyable schema-1 JSON examples under `examples/templates/`, starting with the Issue Fixer and Webhook Task Runner. Copy, edit instance/workspace/Agent IDs, preview via `taskcircuit apply --dry-run` and apply through the existing path. A template is a file, with no runtime entity or separate registry. Defer `template list/show/init` unless operator testing demonstrates a need.

Phase 1 exposes active Source diagnostics through `taskcircuit doctor`. Report sanitized per-instance `starting`, `healthy`, `degraded`, `failed` and `stopped` state, with last transition and reason. Startup errors also appear in CLI/runtime logs when the Hub cannot serve diagnostics. Feishu health can reflect the latest attempt and configuration readiness. Doctor reads state without sending a notification or contacting providers. State is process-local. Notification receipts remain durable.

## Storage and release gates

Schema 10 is sufficient for the proposed ingress receipts, Root links, existing notification deliveries and immutable Automation snapshots. There is no cursor or credential table. A later requirement for polling checkpoints or unreconstructible replay state needs a separate Migration 11 proposal and upgrade/rollback plan. TaskCircuit does not guarantee exactly-once external side effects. Event deduplication cannot retract a successful external request or prevent a repeated Feishu send after a lost result.
