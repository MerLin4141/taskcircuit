# TaskCircuit v0.2 Phase 5 — Loop Limits and Autonomous Continue

## Scope

The automation path now freezes finite Root limits and admits each Agent start through the Hub's serialized SQLite claim transaction. The default is `maxRuns: 8` and `maxDurationSeconds: 7200`; trusted immutable Definition versions may set `loop.maxRuns` to 1–1000 and `loop.maxDurationSeconds` to 1–31536000. A Root stores `max_runs` and the absolute UTC `deadline_at` derived from its trusted creation time, never from Event `occurredAt` or payload. Manual and legacy Roots retain existing behavior. Migration 10 affects only Generation 2. Existing automation Roots without explicit loop settings receive the new finite defaults based on their recorded creation time; this is a migration policy, not a claim those historical limits existed before this version.

## Admission and run accounting

`src/execution-admission.ts` implements the common admission decision for initial work, Continue, answer, Later and retry. Claim runs inside `BEGIN IMMEDIATE`; it checks Root state, other active/uncertain executions, frozen limits, an immutable authorized Decision and current trusted profile/workspace snapshots. The Worker performs a second lease/authorization/deadline check immediately before invoking its adapter, uses the frozen authorized workspace, and checks monotonic and wall-clock elapsed time. Local process control is not an OS sandbox, and arbitrary wall-clock or filesystem changes between separate instructions cannot be made globally atomic with external process creation.

A durable claimed `started_at` counts conservatively as a run because the Agent may have started after a crash. A failed Execution with trusted `safeToRetry: true` proves the process did not start and is excluded; unknown outcomes count and block automatic retry. Continue remains an Agent suggestion; the Hub records it first and materializes at most one successor by unique parent identity in a transaction. Competing Work Items defer while a Root is busy. At a limit the Root records `loop_max_runs_reached` or `loop_deadline_reached`, pending work is terminated consistently, and the original Continue remains in history. A deadline alone does not interrupt an in-flight Agent; a later start is denied. A late answer remains recorded; Later and safe Retry are checked before creating a new Execution and again on claim.

## Verification and remaining boundaries

All tests use isolated databases, controlled clocks, fake Agents and local processes. Coverage includes real archived v0.1.2 database migration, Generation 1 hash preservation, Migration 10 crash points, schema 11 rejection, pinned Definition and Event trust, real two-process continuation races, last-slot competition, crash recovery, receipt response loss, unknown outcomes, pre-start retry, Answer, Later, deadline while running, worker startup recheck, clock rollback, fake multi-run and infinite loops, 100 fake Continue results, and existing P0/P1 / scheduler / fake CLI / Windows Runtime regressions. Fake tests do not prove current external CLI or provider compatibility.

Real Codex and Claude were not invoked; the formal user database and Runtime were not touched; Windows reboot/logon was not performed. Root-wide cancellation, cost/token limits, budget settlement, plugins and external actions remain out of scope. External side effects are not exactly-once and terminating a local process cannot undo an external request. Final execution results are recorded below only after they have actually run.
