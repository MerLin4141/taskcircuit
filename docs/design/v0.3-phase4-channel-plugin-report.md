# v0.3 Phase 4 Channel Plugin report

## Before and after

The Hub formerly constructed `LocalConsoleChannel` directly for every configured instance. The Hub registry now registers the `local-console` Channel Plugin alongside the `local` Source Plugin. At startup the Hub resolves the trusted configured type and creates a `NotificationChannel` for each configured instance ID. Plugin ID and persisted `notification_deliveries.channel_id` are separate. Direct `HubOptions.channels` injection remains supported for existing callers and tests.

## Delivery semantics and trust

The dispatcher remains responsible for notification creation, claims, 30-second leases, updates, failure recording, five-second retry and the three-attempt limit, and notification resolution. The plugin calls the existing `deliver` contract. Results remain independent from committed Agent results; no exactly-once external delivery is promised. Only trusted composition and config select the plugin. Plugin code runs as the local user and is not OS-sandboxed. No config or CLI syntax, external loading, third-party channels or database schema is added.

## Verification

`tests/channel-plugin-integration.test.ts` exercises builtins, manifest/API version and duplicate checks, unknown plugin rejection, two instances of a test-only plugin, real Hub dispatch, retry and direct injection. `tests/realtime.test.ts` covers notification resolution, expired lease recovery, attempts and direct injection; source integration regression retains existing Source behavior with the new Hub composition. Tests use local fakes and temporary databases.
