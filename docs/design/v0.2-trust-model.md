# TaskCircuit v0.2 — Trust Model

> 设计边界，不是现有 OS 安全能力证明。当前 `src/agents/protocol.ts` 明确把 Event context 序列化进 Agent prompt；当前 `src/worker.ts` 创建受用户身份控制的工作目录，Trusted Local 不是安全沙箱。完整证据见 [当前架构](v0.2-current-architecture-map.md)。

## 控制面与数据面

可信控制面：由授权本机操作者配置、版本化并受完整性保护的 TaskCircuit config、policy、Agent Profile、workspace assignment、capability rules、Root Budget。可信是部署假设而不是当前服务已提供多用户鉴权。禁止通过 Event payload、Agent 文字、tool output、远程文本、webhook body 设置可执行文件、cwd、workspace、权限、capabilities、trust level、system command、预算或 policy version。

| 不可信输入                | 可进入 Agent prompt?                                         | 可选择 cwd / Agent?                                        | 可请求 Action?                    | 可授权 Action?                                                         |
| ------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- | --------------------------------- | ---------------------------------------------------------------------- |
| External Event payload    | 可以，尺寸/类型限制与数据标记，视为可能包含 prompt injection | 否；只读可信路由字段由入站规则安全映射，payload 不提供权限 | 仅作为建议/业务资料               | 否                                                                     |
| Webhook body              | 同上；先认证传输来源再解析，认证来源不意味着内容可信         | 否                                                         | 可建议                            | 否                                                                     |
| Agent output / feedback   | 后续可作为标记数据，不能覆盖控制 prompt                      | 否                                                         | 仅候选，必须 schema 校验与 policy | 否                                                                     |
| Tool output / remote text | 可作为数据，限制长度和保留                                   | 否                                                         | 可作为证据或建议                  | 否                                                                     |
| Human input               | 可作为数据；批准是单独 authenticated capability              | 不能借普通回答改变 profile                                 | 可建议                            | 普通 answer 否；仅绑定身份、摘要和期限的 approval 可授权特定已批准动作 |

`can suggest ≠ can authorize`。持久 Decision 保存可信配置 revision、版本、原因码、预算预留、action digest 和授权结果。只有可信策略能把建议映射到允许的受控操作；不能把任意文本拼接为命令。

## 关键限制与 fail closed

1. 同用户的 CLI Agent 本身可调用 shell、读写文件、发网络请求或访问凭据；若没有 OS 强制隔离、受限身份和可证明的网络/凭据边界，控制面拒绝/审批不能物理阻止恶意或越权 Agent。防 prompt injection 不等于硬安全边界。
2. v0.2 第一版仅允许可信操作者在 Trusted Local 明确认知风险下使用可信工作；外部不可信来源、自动高风险写操作默认禁用。真正允许不可信内容自主执行前，必须独立验证执行后端的 filesystem/network/credential 隔离与来源认证；本设计不承诺 v0.2 交付生产沙箱。
3. `NeedsInput` 给资料；`NeedsApproval` 必须绑定主体、Root、action/plan/workspace digest、policy version、revision、expiry。旧 Interaction 不证明身份或授权；在没有可信身份服务时远程批准关闭。
4. dedup 的 source identity 由可信 adapter/本地管理通道提供；用户 JSON 不自报 trust level。新事件可关联多个 Root，但内部 child feedback 只能继承执行所属 Root；跨 Root 新建独立状态和预算。
5. 权限实时收紧：历史 Root 的 immutable revision 防止被动扩权，但全局 deny/revoke 在 claim/send 前可阻断；已发外部操作不能撤回。budget 在原子事务预留，unknown 冻结。审计最小化，拒绝把密钥、token、原始 stderr 和外部 session ID 写入普通 timeline。
6. Local loopback 无用户隔离/认证（v0.1.2），不应以公开服务运行或在多租户环境当安全边界；远程登录/RBAC 属后续专门设计。

## 威胁验证草案

用 fake Agent/受控数据验证控制面拒绝 payload 或 feedback 变更 agent/cwd/permission/budget，重复交付不能重启预算，旧租约不能写结果，审批变更后失效，日志/回执不泄漏标识和 secret。额外通过未来隔离后端的 OS 级越权测试，才能证明实际 Agent 进程无法绕过；仅通过 mock 控制面用例不能声称 OS 级防护通过。

## Phase 3 policy boundary

The built-in deterministic policy reads a Root's pinned immutable Definition Version and trusted local agent and workspace registrations. An actionable policy specifies an effect, event types, agent profile ID and snapshot, workspace ID/path/allowed-root snapshot, allowed and requested capabilities, and explicit approval requirement. Event payload is never used to choose these controls. Missing profiles, changed snapshots, invalid paths or capability escalation fail closed. Workspace paths must exist and resolve within the registered allowed root; symbolic links are resolved when evaluating. Filesystem changes after evaluation are not prevented and would need revalidation before a future execution.

Capabilities are policy metadata, not OS-enforced restrictions. Trusted Local is not an OS-level sandbox; the decision does not authenticate a same-user process. Loopback is not authentication. External action authorization and execution are outside this phase, and `external_action` is not authorized by this policy. Approval produces `wait` only; no approval workflow is implemented.
