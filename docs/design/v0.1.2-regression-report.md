# TaskCircuit v0.1.2 回归验证报告

本轮只增加测试、测试夹具和本报告。未修改业务代码、数据库 schema、正式 README、Release Notes 或版本号；未调用真实 Agent，也未操作正式 Runtime 或数据库。结果：**未通过**，一个人为注入的异常调度状态触发唯一约束错误；Linux 真实进程组验证未运行。

## 测试依据和历史库来源

`tests/fixtures/generate-v011-fixture.mjs` 从 Git 基线 `4fb7cf13fd7c243c8d2bd82ece34f75ae37a55df` 提取并构建的 v0.1.1 代码生成 `v011-databases.json`；生成器校验旧版 Hub、Worker、迁移和配置源码的 SHA-256。空库和混合历史库均由旧版 Hub 创建，含旧版 schema 1–4；内容是虚构的测试数据。每次测试先校验数据库字节 SHA-256，再解压到临时目录的副本。未知 metadata 扩展和调度异常状态明确在副本上注入，不属于旧版正常生成的初始数据。

## Ask / Answer / Resume

旧版 waiting/Ask 记录经 Hub 重启后回答，第二次相同回答返回 409；旧 Interaction 保留并变为 resolved，恢复的 Execution 序号为 2，与原 Execution 指向同一 Agent Session，外部会话标识保持一致。完成结果的回执成功保存；历史行中人为加入的未知 metadata 字段仍保留。上述路径使用真实旧数据库、当前 Hub/Worker 和假 Agent，未验证真实外部 Agent。

## Later / Scheduling

- 旧 Later 计划在到期前一毫秒不触发，到期时触发一次；重复 tick 不创建第二 firing。Hub 重启后使用相同 Session 恢复并完成。
- 假 Worker 的 Later 提交已提交后、响应返回前将其强杀；重启 Hub 和另一 Worker 后仍恢复同一 Session。
- 取消旧 Later 后重启、到期，不触发计划或生成新 Execution。已有并发调度测试使用两个隔离调度进程，专项回归通过。
- 在副本中把已完成的旧计划设置为 active、使用新的到期时间，测试确认已完成任务不被重开。
- **失败：**人为注入 active 计划，其 `(schedule_id, scheduled_for)` 已有 firing；`tickScheduler()` 在 `src/hub.ts` 的 firing 插入处抛出 `UNIQUE constraint failed`（见 `tests/v011-upgrade-regression.test.ts` 的 `continues scheduling...`）。唯一约束阻止重复 firing，但本次 tick 中断；结合其按到期顺序选择计划的代码，推测持续存在的异常记录可能阻碍后续到期任务，尚未单独动态证明后续任务被阻碍。该状态由测试直接修改临时 SQLite 注入；尚未证明正常 API 或普通崩溃能产生它。失败断言保留，未修改业务代码。

## Retry 和 Unknown

假 Agent 明确标示可安全重试的场景，两个固定退避后成功，检查了到期边界、3 个 Execution 的顺序、相同 Session 和两条 firing。既有 P0 测试覆盖可证明启动失败以及执行结果不明不能重试。旧库中原本可重试但缺少安全启动证明的 `agent_execution` 在调度时保守转为 `execution_outcome_unknown`，原分类保留为 cause；这是兼容语义变化，不应解读为旧错误原样继续自动重试。旧 running Execution 租约过期并重启后不会被自动重新执行。

## 升级及中断

旧库可读取 completed、Ask、Later、Retry、未完成 Execution、历史 Session 和 `agent_execution` 错误；历史记录没有回执时仍可读取。回执、JSON 与 CLI 的相关断言通过。对真实旧库启动新 Hub，在实际 migration 的 `BEGIN IMMEDIATE` 执行后用受控子进程阻塞并强杀，再启动可读取旧 Session 和 Schedule，旧 schema 版本保持 1–4。这验证了已有版本的启动事务中断恢复；没有测试新增 DDL 或 Migration 5 的中断，因为本轮没有迁移。

## Result Receipt 与 metadata

201 次 Execution 的测试验证多条回执、旧记录及未知 metadata 字段保留、Hub 重启后查询、重复结果不重复产生记录，且回执不含外部 Session ID；测试检查输出不包含本次 lease token。一次本机观测中 metadata 为 67,944 字节，前 50 次平均 4.822 ms、后 50 次平均 11.677 ms；这是单次非基准测量，不能推导线上性能阈值，但表明 metadata 体积随回执增长，应后续评估归档或更合适的持久化方式。现有测试未证明所有潜在日志均不泄密。

## Windows 与 Linux

Windows 专项与 scheduling 共 6 个文件、44 项通过；包含临时 Runtime 启停、Job Object 路径、进程关闭及假进程树等既有测试。P0/P1 共 5 个文件、33 项通过，含取消、失权和结果确认测试。没有在本轮进行 Windows 重启、注销、真实 Agent 或交互用户 Task Scheduler 全生命周期测试。

WSL Ubuntu 的内核为 `Linux 6.6.87.2-microsoft-standard-WSL2`，未找到 Linux `node`；找到的 npm 为挂载的 Windows 路径，不能据此认定存在可运行的 Linux Node >= 24。Windows `node_modules` 目录存在，但未建立 Linux 原生依赖可用性。**Linux process-group tests: NOT RUN。** 没有安装系统依赖。现有 `tests/p0-cancellation.test.ts` 的进程树用例是 Agent + child 两层；即使后续在 Linux 运行通过，也不能单凭它声称已验证 grandchild、无关进程隔离或 SIGTERM/SIGKILL 的完整要求。

如需后续在 WSL 验证，可先自行安装用户级 Node 版本管理器，再在 Linux 内使用独立副本，避免改写 Windows 的依赖目录：

```sh
export TASKCIRCUIT_SOURCE="<project-root-in-wsl>"
nvm install 24
nvm use 24
node --version
npm --version
mkdir -p "$HOME/taskcircuit-linux-regression"
tar -C "$TASKCIRCUIT_SOURCE" --exclude=.git --exclude=node_modules --exclude=dist -cf - . | tar -C "$HOME/taskcircuit-linux-regression" -xf -
cd "$HOME/taskcircuit-linux-regression"
npm ci
npm run build
npx vitest run --pool=threads --maxWorkers=1 tests/p0-cancellation.test.ts
```

上述仅运行现有两层测试；完整三层及无关进程验证仍需另写并实际运行，不能将其结果等同于全部 Linux 验收。
