# TaskCircuit v0.4 Phase 1 Active Source report

The Phase 0 architecture was finalized in commit `addf9e6ec02e81ce9e2d9bdf293329ea81ffeb17`. Phase 1 implements Hub-managed Source lifecycle on `v0.4-dev`. Package version remains 0.3.0 and SQLite schema remains 10.

## Plugin compatibility and configuration

The [plugin contracts](../../src/plugins/types.ts), [registry](../../src/plugins/registry.ts) and [loader](../../src/plugins/loader.ts) support Source API 1 and API 2, Agent API 1 and Channel API 1. Source API 2 uses `createSource(config, host)`, `start(signal)` and optional `stop()`. The loader checks the API before selecting the required method. API 1 Source modules keep their passive `ingest` behavior. The built-in local route remains implicit and persists `local-cli` / `trusted_local_cli`. A configured active instance requires Source API 2.

Optional `sources` config maps a configured instance ID to an implementation `type`, an optional `required` boolean defaulting to true, and an optional implementation-specific `config` object. Several instances can select one implementation with independent settings. Routes use the instance ID and type as their match. The existing local schedule and event routes cannot impersonate an active Source.

## Submission and authority

The [active lifecycle owner](../../src/plugins/active-sources.ts) gives a Source a frozen capability with `submit` and `reportHealth`. The submission allowlist contains `sourceEventId`, `type`, `payload`, `correlationKey` and `occurredAt`. The [Hub](../../src/hub.ts) binds the instance ID and `external_untrusted`, then validates its trusted route. The Hub supplies an optional `automationId` from that route after verifying the enabled definition's source, trust, Agent and type bindings. A configured route without an Automation accepts a durable unroutable Event. A configured Automation without a matching definition reports unavailable without committing the delivery. Unsupported types are rejected. `apply` still provisions local rules only. The routed regression seeds a source-scoped definition through the existing persistence helper.

A replay uses the first delivery's stored Root link to reconstruct routing before the Event Core digest check. Duplicate and conflict behavior remains in Event Core, with its existing transaction and no plugin imports. The source's payload stays data and cannot select an Automation, Agent, workspace, budget, capabilities, executable or module. The Host does not give the plugin a database, Hub or mutation API. In-process plugins remain Trusted Local code.

## Readiness, shutdown and diagnostics

The Hub validates instance bindings before opening storage. During readiness it constructs and starts instances in config order with a shared five-second asynchronous startup budget. The submission gate stays closed until startup succeeds. A required failure aborts startup and rolls back started and partially initialized instances. An explicitly optional failure remains visible and leaves other instances available.

Close revokes submissions, aborts instances, and attempts each optional stop hook once, concurrently, with a 1.5-second asynchronous stop bound. The CLI handles launcher IPC during startup and after readiness. It reports stop failures with instance IDs and fixed reason codes. Synchronously blocking third-party code cannot be preempted in-process. Observed runtime failure aborts that instance and disables its submission. Degradation can recover to healthy, and failed instances do not automatically restart.

The existing read-only Hub health response exposes configured active Source instance ID, implementation, API version and state. Doctor displays it in text and JSON. Startup, runtime and stop failures use host-defined reason codes. Health is process-local.

## Phase boundary and tests

Lifecycle tests exercise compatibility, instance binding, durable redelivery, the trusted route, startup and rollback, graceful shutdown and the normal CLI/launcher IPC handshake. The fixture uses isolated temporary state and the existing local management listener. Webhook HTTP ingress, GitHub, Feishu, credential resolution and external rule provisioning remain later work. Phase 1 introduces no migration or new listener.
