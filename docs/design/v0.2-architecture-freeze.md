# TaskCircuit v0.2 — Architecture Freeze / ADR

> Phase 0 决策草案；不代表已实现或批准。v0.1.2 基线和证据见 [当前架构](v0.2-current-architecture-map.md)。本文件冻结可实施语义，执行须逐 Gate 审核；未实现 OS 隔离不是授权不可信执行的保障。

## Root state machine

状态 `created, active, waiting, blocked, completed, failed, cancelled, expired, budget_exhausted`。`waiting` = 可恢复的输入/计划；`blocked` = unknown/策略冲突/需核实，可由具备权限的 operator 在 Root 非终态下通过带证据的核实恢复；budget_exhausted 是终态（不能加钱重开）；到 deadline 为 expired。`completed/failed/cancelled/expired/budget_exhausted` 终态不可 reopen。created 经初始化成功 active；活动执行/输入/计划发生时 active ↔ waiting；unknown 或无法认证结果 → blocked；取消、失败、到期、预算耗尽按同一事务条件更新；完成须全部 WI 终态且无 open interaction、有效未决计划、unknown action/reservation。已有在途进程的终止与最终确认可能晚于 cancel 命令；取消不是副作用撤销。blocked 与 waiting 仍受 deadline；deadline 到期按策略先请求停止，未知结果留待核实，不允许新执行。

## Scope freeze

**MUST v0.2.0**：Definition revision / Root / ownership；可信本地来源的版本化 Event、dedup 与 correlation；Decision 可解释；结构化 Feedback `continue/complete/needs_input/later/failed/stop/unknown`；root execution/call/depth/deadline 预算、熔断；timeline、cancel、旧 API/SQLite 升级。可信 source 是系统分配的身份，不能让 payload 自报来源。

**SHOULD（非 Gate，可延后）**：NeedsApproval 的数据/语义设计；ActionIntent、Outbox 的 schema 和只在测试/fake transport 的骨架；不开放未经审核的真实外部写动作。新增 `emit_event` 只能继承 Root 并通过预算与策略，若 v0.2 交付则内部受控类型；不得默认变成任意 webhook。

**DEFERRED**：稳定第三方插件体系/任意加载、跨机器 Hub/共识、广泛渠道/浏览器生态、可视化流程编辑器、生产 sandbox、外部 exactly-once、多用户/RBAC。缺少 OS 强制隔离和认证时绝不宣称恶意同用户进程被限制。

详细状态、预算、交付和并发协议分别见 schema、API、failure、trust 与 test strategy。Phase 0 无代码或数据库修改。

## 预算维度与熔断的可验证边界

| 维度                    | 分类           | v0.2 建议语义                                                                                                                 |
| ----------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| max_executions          | HARD           | 每次创建可启动执行在事务中预留并记账；Retry、Continue、回答后恢复和 Later 都计入。                                            |
| max_agent_calls         | HARD           | 每次 Agent 调用前预留；明确 OS 启动失败可按证据释放 call，但执行 attempt 已计；无法确认时冻结。                               |
| max_depth               | HARD           | 可信控制面计算内部反馈/子事件深度；外部输入不得填高权限 root/depth；超限不入队。                                              |
| deadline / max_duration | HARD admission | Root 创建时以较早的绝对 deadline 与 created+duration 固定；禁止超时后新启动，并请求停止在途 Agent；无法保证外部执行即时终止。 |
| max_tokens / max_cost   | UNAVAILABLE    | provider 缺少可靠上限和可核验用量时不承诺强制；可记录可信遥测作为 SOFT 诊断，不得把它表示为硬限额。                           |

Loop breaker 在每次决策前基于 Root 内持久记录判断：最大执行/调用/深度/期限、同一 feedback 类型+规范化摘要连续重复、同一内部 event 的稳定 fingerprint 重复、同一 action proposal `(target,kind,request_digest)` 连续重复、连续可证明失败。阈值由可信不可变定义提供，超限分别转 `blocked` 或 `budget_exhausted` 并给 reason；阈值必须有有限正整数，不能由 Agent 建议修改。去重 delivery 与重复业务内容不是同一判定：对业务内容只根据 policy 决定是否熔断，不凭摘要合并事件。记录 fingerprint 而不是默认记录原文；hash 不是保密手段。

审查中若需要调整预算，只允许在 Root 未终态、验证操作者与上层安全硬上限后通过版本化事务记录旧值/新值/理由；deadline 已过或 Root 已终态禁止重新激活。默认实现无需提供在线调额 API，可仅在新 Root 指定可信预算。失败与 unknown 的区分按安全证据，不使用错误文案猜测副作用是否发生。

## Architecture Freeze Addendum — Scope Simplification

**Precedence:** this Phase 3.5 addendum supersedes conflicting prospective scope and deadline behavior in the historical Phase 0 text above; it does not rewrite Phase 0 history or claim that planned features are implemented. The user has also selected the Phase 3 behavior: authorization records a Work Item creation intent and the Root remains `created` until a later stage materializes it. [Scope audit](v0.2-scope-simplification.md) and [implementation plan](v0.2-implementation-plan.md) contain the active proposal.

**Unchanged invariants:** Root lifecycle and terminal/successor semantics; immutable pinned Definition Version; Event identity, deduplication and per-Root correlation; trusted policy inputs; immutable Decision and idempotent recovery; Agent suggestions do not authorize themselves; the single active/unknown-blocked execution constraint; lease/fencing, safe retry, receipts and unknown outcome safeguards. Schema 8 and Decision remain as implemented. Trusted Local is not OS isolation, and external exactly-once effects are not guaranteed.

**Reduced v0.2 scope:** user-facing Automation, Event, Root, Agent and Inbox; internal Work Item, Execution, Decision, Policy, Interaction and Session. The minimal future feedback set is Complete, Continue, NeedsInput, Later, Failed and Stop. Reuse existing Ask/Answer and Later/Scheduler paths with integration tests. No separate Policy product, DSL, Approval Engine, ActionIntent, Outbox, general external action dispatcher or plugin architecture in v0.2. Complex budget/call/depth/reservation/settlement accounting and token/cost limits are deferred. Plugin architecture is tentatively v0.3; ecosystem integrations are tentatively v0.4.

**Loop admission replaces complex budget:** finite trusted `max_runs` and a fixed Root deadline are the v0.2 safeguards. All Agent starts, including initial execution, Continue, Retry, answer and Later, count. Check Root state, the remaining limit, deadline and single-active constraint atomically at admission; if a crash leaves start uncertain, block or count conservatively. At the deadline do not start another Agent. Unlike the old Phase 0 proposal above, reaching the deadline alone does not automatically stop an already running Agent; explicit cancellation and lease-loss safeguards remain. Do not overwrite a late result or unknown outcome. If current schema cannot support correct durable admission, propose a minimal migration first. Do not expose autonomous Continue before these protections are enforced.

**Remaining gates:** Phase 4 Minimal Feedback Loop; Phase 5 Loop Limits; Phase 6 Autonomous Loop E2E & UX; Phase 7 Release Preparation. Later real Agent tests and release actions need separate authorization. These scope changes are design decisions and leave existing source, databases and the Phase 0 record unchanged.
