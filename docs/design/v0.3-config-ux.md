# TaskCircuit v0.3 Declarative Configuration UX

Status: **proposed design, not a supported v0.2 command or configuration format**. The architecture boundary and trust assumptions are in [the plugin freeze](v0.3-plugin-architecture.md). The public mental model remains Automation → Event → Root → Agent.

## Current v0.2 experience

`src/config.ts` reads a trusted JSON file with `agents`, `routes`, optional `policyWorkspaces`, `channels`, and `schedules`. `src/hub.ts` Automation creation checks the agent, event route and canonical registered workspace before persisting a definition and immutable version. `src/decision-core.ts` later compares the pinned workspace snapshot to the current trusted workspace and policy. `docs/quickstart-v0.2.md` demonstrates registration, Hub/Worker startup, `automation create`, then `event emit`. There is no `taskcircuit apply` today. Agent choices and local-console are currently hard-coded; the design does not claim these are plugins already.

## Goal: one rule ≈ one automation

Illustrative **future** trusted rule file (not executable with v0.2):

```json
{
  "rules": [
    {
      "name": "bug-fixer",
      "when": { "source": "local", "type": "coding.task" },
      "agent": "codex",
      "workspace": "C:\\workspace\\my-app",
      "instruction": "修复测试失败并运行测试",
      "loop": { "maxRuns": 8, "deadline": "2h" }
    }
  ]
}
```

An operator chooses the actual directory and policy; examples do not grant permissions. The file is trusted input. Incoming event payloads are data and cannot choose or change these values. A rule does not turn capability labels into filesystem isolation. A source instance is bound by trusted configuration, not a self-declared event field. `loop.deadline` needs a bounded parser and a fixed duration meaning; it is not a deadline supplied by an event.

## Rule → trusted internal model

| Rule field                      | Compilation target                                                                        | Required validation                                                                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                          | stable Automation Definition identity/name                                                | unique, stable across repeated applies; explicit conflict against existing manually managed definitions                                |
| `when.source`, `when.type`      | trusted source binding and Route event match                                              | registered Source and allowed type; reject ambiguous/duplicate matches; do not trust payload for binding                               |
| `agent`                         | Agent Profile / plugin implementation reference in the trusted definition                 | registered profile and compatible Agent Plugin; no executable or module path from events                                               |
| `workspace`                     | Workspace Policy ID, canonical path and allowed root in the immutable definition snapshot | real path exists and is under an explicitly trusted allowed root; policy determines requested and allowed capabilities, not event data |
| `instruction`                   | trusted Automation Version instruction                                                    | validated operator text; event and answer data stay separately marked as data                                                          |
| `loop.maxRuns`, `loop.deadline` | bounded loop limits in Automation Version snapshot                                        | finite positive values within existing policy; no payload can increase them                                                            |

An implementation must reuse Agent Profile, Workspace Policy, Route, Automation Definition and immutable Automation Version rather than introducing a second scheduler or authority. Defaults must match v0.2 where compatibility requires them. The example omits allowed roots and capabilities intentionally: apply must reference already trusted policy or require an explicit operator-authored policy; it must not infer a broad permission from an arbitrary path. UI may explain missing prerequisites in plain language.

## Explicit apply recommendation

Conceptual future commands:

```text
taskcircuit apply ./automations.json
```

The command reads the named trusted file, validates and compiles a deterministic plan, reports creates/versions/unchanged/conflicts and only then applies. Hub startup reads its existing configuration and does not implicitly mutate definitions. Identical canonical content is a no-op; changed trusted content creates an immutable version. Existing Roots stay pinned; only subsequently created Roots use a new version. Existing manually created definitions are never silently adopted, overwritten or deleted. Removing a rule from a file does not silently disable an existing Automation. Exact command flags and conflict-resolution UX remain open until implementation.

All intended database writes should commit or roll back as one transaction; no partially installed Automation versions. If trusted runtime configuration also needs file changes, DB and filesystem are separate resources: do not promise a single atomic commit. Apply must either require the runtime configuration as an already validated prerequisite or define an explicit staged activation and recovery protocol. A crash before commit leaves old DB state; after commit, restarting must observe the committed version. An unavailable or mismatched runtime configuration must fail closed, not apply a weaker policy.

## Compatibility strategy

Existing v0.2 config and CLI (`automation create/list/show`, `event emit`, `root list/show`, `inbox`, `answer`, `watch`, `doctor`, `runtime`) remain valid. Existing source, Agent and channel names and old Root snapshots remain stable. A new rule file is additive; installing v0.3 does not require immediate migration of existing configs. No automatic re-creation of Automations during upgrade. Configuration resolution is anchored to the trusted config file; external plugin loading remains explicit and never installs packages. The local filesystem and installed plugin modules are trusted code, not an OS sandbox.

## Validation before implementation is accepted

Use isolated v0.2 database fixtures and fake plugins to test deterministic compile/apply/reapply, update pinned versions, invalid workspace and capabilities, route collision, manual-definition conflict, missing plugin/API mismatch, crash before and after DB commit, startup after partial activation, and event payload attempting to override trusted choices. Test existing CLI/config and all existing Agent, scheduling, notification, cancellation and receipt regressions. No external calls or real user runtime. If the required durable ownership or atomicity cannot be expressed safely in schema 10, stop and present a migration proposal rather than creating Migration 11 without review.
